## 1. Canonical architecture

Mindclade is an agent-native scientific engineering platform. The repository is the operating environment. External systems are replaceable adapters, not architectural authorities.

```text

                               AUTHORING

          +-----------------------+----------------------+
          |                       |                      |

                                                    - Science

          |                       |                      |
          +-----------------------+----------------------+

                      |   Rust compiler    |
                      +---------+----------+
```

### Forge consolidation

Historical drafts used `forge/` as an independent compiler authority. The final greenfield design retires that split.

- `codegen/` is the only compiler/generator root.
- The normalized Semantic Graph is the compiler authority.
- "Forge" may remain as a historical product name, compatibility alias, or generated documentation term, but not as a separate top-level compiler system.
- Any future use of the Forge name must resolve to `codegen/` packages and the Semantic Graph/Capability Graph pipeline.

## 3. Root responsibilities

| Root | Responsibility |
| --- | --- |
| `contracts/` | Authored interface, resource, science, agent, operator, schema, and registry authority. |
| `codegen/` | Sole compiler/generator. Parses authored inputs, builds Semantic Graph and Capability Graph, emits projections. |
| `core/` | Shared primitives: identity, evidence, policy, provenance, artifacts, errors, graph identity, time. |
| `biology/` | Mindclade-owned biological semantics and scientific entity model. |
| `data/` | Source ingestion, normalization, datasets, features, lineage, quality, and knowledge systems. |
| `compute/` | Tensor, native, kernel, operator, distributed, parity, and performance substrate. |
| `models/` | Model families and model-specific architecture. |
| `ml/` | Training, posttraining, evaluation, checkpointing, qualification, recipes. |
| `runtime/` | Model execution, inference, batching, serving, distributed runtime, telemetry. |
| `platform/` | Control semantics, RuntimeKit, TestKit, artifacts, events, identity, tenancy, policy, audit, persistence. |
| `agents/` | Agent runtime, context, planning, tools, skills, approvals, sandboxing, adapters. |
| `protocols/` | Published protocol projection surfaces and descriptor bundles. |
| `products/` | User/developer-facing products: SDKs, CLI, MCP, CDK, console, admin, docs site, design system. |
| `services/` | Deployable processes. Services orchestrate platform/domain packages; they do not duplicate domain frameworks. |
| `infra/` | Authored infrastructure modules and environment configuration. Generated deploy artifacts are projections. |
| `generated/` | Disposable generated output with provenance. Never an authority. |
| `tests/` | Cross-cutting test, conformance, compatibility, qualification, reproducibility, and scientific validation suites. |
| `tools/` | Repository, architecture, generation, release, qualification, provenance, and developer automation. |
| `docs/` | Human-facing documentation and generated architecture package. Source models remain machine-readable. |

## 4. Architecture laws

1. One semantic authority: the normalized Semantic Graph is the compiler authority after authored inputs are parsed and validated.
2. One compiler: `codegen/` owns parse, normalize, validate, resolve, lower, plan, and emit.
3. Generated output is disposable. It is regenerated, byte-checked, and provenance-tracked; it is never hand-edited into authority.
4. Thin services only. Services own deployment process boundaries and orchestration, not duplicate training, runtime, data, or agent frameworks.
5. Every diagram box must resolve to one of: repository package, generated artifact, external boundary, or explicitly marked future capability.
6. External systems are adapters. GitHub, Linear, Notion, Retool, Datadog, cloud providers, and model providers may integrate, but they do not become source authority.
7. Contracts and descriptors lead. Runtime behavior, SDKs, MCP tools, CDK, Terraform, docs, and deployment manifests derive from contracts and source descriptors wherever practical.
8. Provenance is mandatory. Engineering and scientific claims require receipts, immutable artifacts, hashes, inputs, tool versions, and review state.
9. Qualification is fail-closed. Missing CI, missing cloud proof, missing connected runtime proof, or missing scientific evidence is `BLOCKED`, not `PASS`.
10. No duplicate roots. If two roots implement the same compiler, runtime, provenance, agent, training, or artifact system, one must become the owner and the other must become an adapter, generated surface, or be removed.
11. Architecture is generated from source models. Posters and atlas diagrams are outputs, not hand-maintained authority.
12. Authored boundaries must be owned. Every source package has a code owner, maturity state, dependency policy, and validation lane.

## 5. Dependency and ownership rules

### Core direction

```text
contracts + architecture source models
        |
        v
codegen
        |
        v
generated projections
        |
        +--> protocols
        +--> products/sdk
        +--> products/mcp
        +--> products/cdk
        +--> infra/generated
        +--> docs/generated

core
        |
        v
biology / data / compute / models / ml / runtime / platform / agents
        |
        v
services
        |
        v
public APIs and event streams
        |
        v
products: console / CLI / SDK / MCP / admin / docs site
```

### Rules

- `core/` cannot depend on `services/`, `products/`, or cloud-specific infra.
- `contracts/` cannot import generated products as authority.
- `codegen/` reads authored contracts, architecture models, descriptors, and registries; it emits into `generated/`, `protocols/`, and generated subtrees.
- `generated/` cannot be imported as source authority by `contracts/` or `codegen/`.
- `services/` may depend on domain packages and `platform/`, but must not reimplement domain packages internally.
- `products/sdk` consumes generated protocol/API surfaces and stable public runtime helpers.
- `products/console`, `products/cli`, and `products/mcp` consume public APIs, SDKs, and descriptors, not private service internals.
- `infra/` owns deployable topology source. Environment-specific generated manifests must be derived and checked.
- `docs/architecture/generated` is generated from `docs/architecture/model` and repository descriptors.
- `tests/qualification` can depend broadly, but production code cannot depend on tests.

## 7. RuntimeKit

`platform/runtimekit` is the standard runtime envelope for every deployable service and worker. It prevents each service from inventing its own lifecycle, configuration, health, identity, telemetry, and shutdown behavior.

RuntimeKit owns:

- Process lifecycle: start, ready, drain, shutdown.
- Configuration loading and validation.
- Service identity and workload identity integration.
- Health checks: liveness, readiness, startup, dependency health.
- Middleware: request IDs, auth context, policy checks, tenant boundaries.
- Telemetry: logs, metrics, traces, spans, exemplars, service metadata.
- Error mapping and failure classification.
- Event/outbox hooks.
- Artifact/provenance hooks.
- Service descriptor loading.
- Local development entrypoints.

Every service must register a `ServiceDescriptor@v1` and run inside the RuntimeKit envelope unless explicitly exempted by an ADR.

## 8. TestKit

`platform/testkit` is the standard test harness for deterministic service, runtime, and agent validation.

TestKit owns:

- Fake clock and deterministic time.
- Fake identity and tenant contexts.
- Fake artifact store and content-addressed storage.
- Fake event bus/outbox.
- Fake workers and schedulers.
- Fake model/runtime endpoints.
- Database and migration fixtures.
- Generated contract fixtures.
- Assertion helpers for provenance, telemetry, policy, and descriptor behavior.
- Golden test support for generated surfaces.

TestKit must not become a second runtime. It mirrors RuntimeKit interfaces and allows focused validation without live cloud dependencies.

## 9. ServiceDescriptor@v1

Every deployable process has one descriptor at:

```text
services/<service_name>/service.descriptor.yaml
```

Workers use the same schema:

```text
services/workers/<worker_name>/service.descriptor.yaml
```

Minimal descriptor shape:

```yaml
apiVersion: mindclade.dev/ServiceDescriptor@v1
kind: Service
metadata:
  name: inference-service
  package: services/inference_service
  maturity: planned | experimental | partial | production
  owner: team-or-person
  description: Serves qualified model releases for inference workloads.

contracts:
  resources:
    - contracts/typespec/services/inference
  protobuf:
    - contracts/protobuf/mindclade/inference
  events:
    publishes:
      - mindclade.inference.result.v1
    subscribes:
      - mindclade.model.release.qualified.v1

runtime:
  runtimekit: required
  language: go | rust | python | typescript
  entrypoint: path/to/main
  configSchema: contracts/schemas/deployment/inference-service.schema.json
  health:
    liveness: /healthz
    readiness: /readyz
    startup: /startupz

dependencies:
  services:
    - artifact-service
    - model-service
  storage:
    - model-artifacts
    - inference-results
  databases:
    - control-plane-postgres
  queues:
    - inference-requests

security:
  identity: workload-identity
  tenancy: required
  authorization:
    policy: contracts/agents/policies/inference-policy.yaml
  secrets:
    - model-registry-reader

artifacts:
  reads:
    - model-manifest
    - checkpoint
  writes:
    - inference-result
    - evidence-bundle

provenance:
  emitsReceipts: true
  requiredFields:
    - input_artifact_hash
    - model_release_hash
    - runtime_version
    - policy_decision_id

telemetry:
  metrics:
    - request_count
    - latency
    - batch_size
    - model_version
  traces: required
  logs: structured

deployment:
  environments:
    - dev
    - staging
    - production
  topology:
    cpu: required
    gpu: optional
  scaling:
    minReplicas: 1
    maxReplicas: 20

qualification:
  source:
    - generated-drift-check
    - contract-conformance
    - unit-tests
  runtime:
    - runtimekit-health
    - testkit-fixtures
  deployment:
    - kubernetes-schema-check

```

Descriptor rules:

- The descriptor is authored.
- Codegen consumes it to synthesize deployment IR, docs, checks, service catalog entries, and topology diagrams.
- CI validates descriptor schema, owner, maturity, dependency policy, and existence of referenced paths.
- Missing descriptor means the process is not a recognized Mindclade service.

### Qualification lanes

Qualification is staged and fail-closed.

| Lane | Proves | Does not prove |
| --- | --- | --- |
| Source qualification | Tree integrity, architecture laws, generated drift, static checks, unit tests. | Live deployment, remote CI, cloud runtime, scientific validity. |
| Runtime qualification | RuntimeKit/TestKit behavior, service health, local integration, descriptor behavior. | Production readiness without connected infrastructure. |
| Deployment qualification | Manifest validity, policy conformance, topology synthesis, GitOps bundle integrity. | Successful production rollout unless connected GitOps confirms it. |
| Connected qualification | Cloud/provider/runtime integration against real services. | Scientific claim validity by itself. |
| Scientific qualification | Data lineage, numerical parity, benchmarks, review state, claim evidence. | Infrastructure health by itself. |
| Release qualification | Signed artifacts, SBOM, provenance, release notes, promotion evidence. | Future environment behavior after drift. |

### GitOps flow

```text

  v

  |
  v

  |

  |
  v
post-deploy verification
  |
  v

```

No deployment is considered qualified until the relevant environment produces evidence. A valid manifest is not a deployed system.

## 11. Engineering provenance model

Engineering provenance binds intent to production behavior.

```text
requirement
  -> spec
  -> ADR
  -> contract
  -> source
  -> generated artifact
  -> test
  -> evaluation
  -> build
  -> signed artifact
  -> deployment
  -> telemetry
  -> incident
  -> remediation
  -> updated requirement
```

Required engineering receipt fields:

- Requirement or issue ID.
- Spec path.
- ADR path when architecture changes.
- Contract path and version.
- Source paths and commit.
- Generated artifact manifest.
- Test commands and outcomes.
- Build environment.
- Artifact hashes.
- SBOM reference.
- Signature and signer identity.
- Deployment target and environment.
- Telemetry evidence reference.
- Review/approval state.

Engineering provenance is used to answer:

- Why does this system exist?
- Which contract defines it?
- Which generated outputs came from it?
- Which tests qualified it?
- Which artifact was deployed?
- Which environment is running it?
- What telemetry confirms behavior?

## 12. Scientific provenance model

Scientific provenance binds data, computation, model behavior, inference, and claims.

```text
source record
  -> quarantined raw object
  -> curated record
  -> entity
  -> dataset snapshot
  -> split manifest
  -> feature set
  -> experiment
  -> training run
  -> checkpoint
  -> model manifest
  -> evaluation report
  -> qualified release
  -> inference result
  -> artifact
  -> evidence
  -> claim
```

Required scientific receipt fields:

- Source database or lab source.
- Source access date and license.
- Raw object hash.
- Curation transform and version.
- Entity identifiers and ontology mappings.
- Dataset snapshot hash.
- Split manifest hash.
- Feature schema and transform version.
- Experiment protocol.
- Training run configuration.
- Code commit and environment.
- Checkpoint hash.
- Model manifest hash.
- Evaluation metrics and benchmark corpus.
- Review state: computed, retrieved, inferred, human-reviewed, or rejected.
- Claim scope and uncertainty.

Scientific provenance is used to answer:

- Where did this data come from?
- What transformation touched it?
- Which model saw it?
- Which checkpoint produced the result?
- Which evaluation supports the claim?
- Is the claim association, prediction, causal claim, or hypothesis?
- What evidence is missing?

- Architecture generated views reflect changed components and edges.
- Provenance receipts can identify input, generator, source commit, output, and validation evidence.
- Qualification status is accurately recorded.

## 17. Trust and security boundaries

Trust boundaries must be visible in architecture and enforced in code.

Required boundaries:

- Tenant boundary.
- Workload identity boundary.
- Human/agent approval boundary.
- Secret boundary.
- External API boundary.
- Data license boundary.
- Raw/quarantined data boundary.
- Model artifact boundary.
- Generated artifact boundary.
- Deployment environment boundary.
- Production access boundary.

Security controls:

- Workload identity for services.
- Least-privilege service accounts.
- Policy-as-code for authorization decisions.
- Signed generated and release artifacts.
- SBOM for release bundles.
- Network policy for service communication.
- Tenant-aware audit logs.
- Provenance receipts for sensitive actions.
- Manual approval gates for destructive or irreversible operations.

## 18. External tool policy

Do not introduce an external tool, SaaS product, framework, database, queue, workflow engine, agent framework, or infrastructure dependency unless it solves a demonstrated requirement that existing Mindclade platform primitives cannot reasonably satisfy.

Approved posture:

- GitHub, Buildkite, cloud providers, Datadog, Linear, Notion, Figma, Retool, and similar systems are adapters.
- Kubernetes is the execution abstraction.
- GCP/Azure provide cloud substrate.
- OpenTelemetry is the observability contract.
- TypeSpec and Protobuf are authored/projection inputs, not competing runtime systems.
- Mindclade owns contracts, orchestration semantics, provenance, capability graph, scientific domain logic, and qualification semantics.

## 19. What must be marked planned

Any architecture component without source, tests, descriptors, generated outputs, and qualification receipts must be marked:

- `planned` if it is design intent only.
- `experimental` if prototypes exist without stable contracts.
- `partial` if source exists but surfaces, checks, or evidence are incomplete.
- `production` only when source, runtime, deployment, security, and operational evidence are all present for the claimed environment.

Architecture diagrams must show this status rather than implying all boxes are equally real.

## 20. Final operating principle

Mindclade's architecture should be legible to both humans and agents:

- Contracts say what exists.
- Codegen explains how projections are made.
- Descriptors say what runs.
- Architecture models say how pieces relate.
- Tests say what is checked.
- Qualification says what can be claimed.
- Provenance says why the claim is trustworthy.

The repository is the source of truth. Posters, dashboards, generated docs, SDKs, MCP tools, deployment bundles, and architecture views are all projections.
