This page documents the consolidated implementation roadmap and acceptance gate sequence for Mindclade engineering. It lists the architecture baseline, foundation acceptance, VS-001 milestones, and work-packet evidence contracts. Use the [current handoff](/developer/agent-handoff) for the verified integrated checkpoint and the [remaining work checklist](/architecture/vs001-todo) for current slice status.

The architecture baseline is consolidated, but implementation is not complete. The [master blueprint](https://github.com/Mindclade-org/mindclade-internal-monorepo/blob/main/docs/architecture/MASTER_BLUEPRINT.md) and [maturity](https://github.com/Mindclade-org/mindclade-internal-monorepo/blob/main/docs/architecture/maturity.yaml) define scope. ADR-015 authorizes the original blueprint scaffold.

| F1 — Qualified engineering factory | Work packets, admission, ownership, policy, budgets, combined integration and release sets | Applicable Q01–Q24 cases pass for a named work class under exact policy; restricted identities and audited effects | Planned |
| S1 — Protein-first semantics/data | Biological identities, units/context, pinned local data/literature fixtures, splits and lineage | Cross-binding semantics, deterministic ingestion, validated leakage controls and source-permitted use | Planned |
| S2 — Shared representation | Clade representation / Clade-Embed plus a bounded molecular baseline | Frozen independent evaluation, held-out baselines, measured quality/cost and reproducible artifacts | Planned |
| C1 — Optimized compute/runtime | Operator ABI, CPU references, TileLang only for measured need, real model executor | Forward/gradient and compatibility matrix plus qualified runtime eligibility; cancellation and paid-effect recovery | Planned |

Gate IDs are planning labels, not existing workflow engines or automation jobs. A gate can have multiple reviewed slices. No gate passes solely because its directory, schema, BUILD file, test name or design document exists.

## VS-001 delivery milestones

1. Freeze one representative contract and its independently authored expected behavior, compatibility cases, error semantics and source provenance.
2. Pin the official frontend and extract complete versioned SemanticInput@v1. Reject unsupported versions, unresolved references and ambiguous lowering.
3. Build and seal MindcladeGraph with typed views; compare relevant compatibility. A generated manifest is an intermediate compiler milestone only.
4. Emit the required protocol/API/client/MCP/docs surfaces for the representative capability. Exercise at least one real generated consumer against TestKit's deterministic service using independent expected results.
5. Compose RuntimeKit service and deterministic worker from ServiceDescriptor@v1. Commit Run state and outbox atomically in PostgreSQL and enforce duplicate, stale-ownership, crash/retry, artifact-integrity and cancellation behavior.
6. Seal the replay capsule with exact source, tools, graph, manifest, run, artifact, evidence, evaluator, policy and decision identities. Changed inputs invalidate affected evidence. A separate assurance owner assesses the declared claim.

The detailed plan and failure checks remain in the VS-001 spec. Additional languages, real model training, cloud deployment, paid campaigns and laboratory execution do not enter its exit criteria through this roadmap.

The current foundation covers bounded official frontend extraction, immutable typed graph construction, graph/manifest projection, checked B2a TypeScript/Rust consumers and B3a service descriptor/configuration compilation. Public protocol products, a RuntimeKit/TestKit service, dependency enforcement, PostgreSQL/outbox execution and replay remain planned. The audited compiler/governance branches are integrated at the checkpoint in the current handoff. Preserve later concurrent work and do not advance maturity merely because a plan or path exists.

## Work packet and evidence contract

Before activation, each slice records the following across its reviewed specification, packet, acceptance descriptions, stop conditions and operator environment controls. This checklist does not add fields to WorkPacket@v1:

- Objective, exclusions, source/base revision and exact contract versions.
- Owned paths, allowed dependencies, implementation owner and independent reviewer.
- Acceptance criteria/evaluator revision fixed before candidate implementation.
- Capabilities, permitted callers, network/credential scope and mutation ceiling.
- Budget, reservations, retry/cancel/recovery rules and stopping conditions.
- Required artifacts, evidence scope, provenance, policy and decision references.

Evidence records the exact command or evaluator, inputs, environment, candidate, integration base, output digests, observed results and limitations. A source pass, runtime pass, numerical result, scientific claim, release and deployment each need their own evidence and decision.

WorkPacket@v1 and GovernanceReport@v1 are non-semantic records, not locks, capabilities or grants. Bootstrap admission remains BLOCKED until operator-approved accepted-policy and packet digests exist. Independent criteria precede candidate implementation; changed packet/specification/policy/base/candidate inputs require fresh admission, affected checks and review. A candidate cannot authorize itself with its own policy changes. See the supervised development guide.

## Completion and failure

Use only PASS, FAIL or BLOCKED for GovernanceReport@v1 and its check statuses. A required unexecuted check is BLOCKED with "not run" in detail or prose, never a fourth enum value. Keep operational state and claim assessment separate. Unknown remote state is not a pass.

A successful fake proves engineering behavior only. Missing GPU, provider, license, reviewer, credentials or protected holdout access blocks the applicable claim rather than being replaced with a host substitute or mocked result.

Implementers may prepare checks and candidate evidence. This repository's author-written regression tests do not establish independent assurance by themselves. Qualification requires the separately controlled acceptance and review path specified in ADR-009.
