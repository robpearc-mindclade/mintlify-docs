This proposed draft from group D of the 2026-09-26 design audit amends the kernel rule in ADR-007 ("No Triton or `tch-rs` baseline dependency is introduced"). Until accepted, that rule, the same line in ADR-015's preserved laws, the code rules in AGENTS.md, and the compute and native policy stand.

| Status | Date | Related |
| --- | --- | --- |
| Proposed | 2026-09-27 | ADR-007, ADR-015, ADR-019, ADR-023 |

## Context

The blanket rule no longer fits the substrate proposed in ADR-019:

- TorchInductor, the default `torch.compile` backend, generates Triton code on GPUs.
- `torch` 2.14.0 declares `triton~=3.8.0` as a Linux requirement.
- Pairformer primitives already have kernels. cuEquivariance provides `triangle_multiplicative_update` and `triangle_attention` for PyTorch.
- FlashPairformer ships custom kernels in the shared runtime of `anthropics/uplifting-biomolecular-modeling`, whose kit code is Apache-2.0.

The current design text asks for pinned CPU references with declared shape, dtype, and device coverage. The compute scaffold already has `kernels/tilelang/`, `kernels/triangle/`, and `kernels/pairformer/`.

## Decision

1. **Kernel ladder.** An operator uses the first rung that meets its declared numerical and cost targets:
   1. A PyTorch/ATen composition, which is also the reference.
   2. Compiler-emitted kernels (`torch.compile`/Inductor, FlexAttention).
   3. An adopted existing kernel with parity qualification, starting with the cuEquivariance triangle ops and FlashPairformer for Pairformer operators.
   4. TileLang or native CUDA, only for a measured gap: a recorded benchmark on declared shapes and hardware showing that rungs 1–3 miss the target.

   No hand-written kernel in Triton, TileLang, or CUDA is added without that measurement.
2. **Triton rule.** The rule becomes "no Mindclade-authored Triton kernels and no direct Triton API use in Mindclade source". Triton is permitted as compiler output, as a pinned transitive dependency of PyTorch, and inside an adopted kernel package. The Rust rule is unchanged: no `triton` crate.
3. **Adopted-kernel qualification.** Each adopted kernel records its pinned package version and digest, its licence and provenance, forward and gradient parity against the rung-1 reference over a declared shape, dtype, and device envelope with dtype-specific tolerances, its determinism, and its fallback for unsupported shapes.
4. **Operator contracts bind to PyTorch's operator system.** An authored operator contract (schema, shapes, dtypes, devices, tolerances, gradient support, determinism) projects to:
   - a `torch.library` registration (`custom_op`, `register_fake`, `register_autograd`), checked with `opcheck`;
   - for native code, the LibTorch stable ABI: `torch::stable` wrappers, `STABLE_TORCH_LIBRARY` and `STABLE_TORCH_LIBRARY_IMPL` with boxed kernels, and a declared `TORCH_TARGET_VERSION`.

   Codegen emits these bindings from the contract.
5. **CPU references are a small-shape oracle.** They run fp32 or fp64 forward and gradient checks on small shapes in CI. They are not a device-coverage gate: a device implementation is qualified on its own device against the oracle over its declared envelope, and a missing CPU path for production shapes blocks nothing.
6. **`tch-rs` stays excluded.**

## Consequences

- At acceptance, coordinated edits follow in ADR-007's consequences, ADR-015's preserved-law list, the AGENTS.md code rules on Triton and TileLang, the architecture laws, the programmable-biology compute row and acceptance text, and master blueprint section VI.
- TileLang stays available but is no longer the default optimised path; `compute/kernels/tilelang/` remains a planned area.
- Adopted kernels belong to compute (ADR-007) with their own licence and provenance record. Models call operators, not kernel packages (ADR-023).
- The cuEquivariance kernel wheel `cuequivariance-ops-torch-cu12` is binary-only under an NVIDIA proprietary licence, while the repository files are Apache-2.0. Using it is a licence and trust-boundary decision.
- Adopting FlashPairformer means Mindclade owns any fork it needs.
- Changing the PyTorch minor version, the stable-ABI target, or an adopted kernel version makes the affected parity evidence stale.
- Nothing here adds a dependency or kernel; gate C1 remains planned.

## Alternatives considered

The prior blanket rule ("No Triton or `tch-rs` baseline dependency") was the baseline. It was rejected because it no longer fits the PyTorch 2.x substrate where Triton is generated by Inductor and declared as a transitive dependency.
