Most integration problems with MindClade fall into a handful of well-known categories — a mismatched API key, a webhook endpoint that isn't publicly reachable, or a cursor that expired between pages. Work through the relevant section below to identify the root cause and apply the fix. If you still can't resolve the issue after following these steps, the support team is ready to help.

## Authentication Errors (401 / 403)

A `401 Unauthorized` means the server could not authenticate your request at all. A `403 Forbidden` means it authenticated you but your key lacks permission for that action. Both usually have a clear root cause.

<Accordion title="Wrong key format">
  **Symptom:** Every request returns `401` with `"code": "invalid_api_key"` immediately, even on simple `GET` requests.

  **Cause:** The `Authorization` header is malformed. The API requires the `Bearer` scheme — omitting it, or using a different scheme like `Token` or `Basic`, causes instant rejection.

  **Fix:** Ensure your header looks exactly like this:

  ```http
  Authorization: Bearer mk_live_abc123xyz456
  ```

  Check for accidental whitespace, newline characters, or URL-encoding artifacts if you're constructing the header programmatically.

  ```javascript
  // ✅ Correct
  headers: { "Authorization": `Bearer ${process.env.MINDCLADE_API_KEY}` }

  // ❌ Wrong scheme
  headers: { "Authorization": `Token ${process.env.MINDCLADE_API_KEY}` }

  // ❌ Missing "Bearer"
  headers: { "Authorization": process.env.MINDCLADE_API_KEY }
  ```
</Accordion>

<Accordion title="Expired or revoked key">
  **Symptom:** Requests that worked yesterday now return `401` with `"code": "api_key_revoked"` or `"api_key_expired"`.

  **Cause:** The key was revoked manually in the dashboard, or it reached its expiry date if you set one at creation time.

  **Fix:**
  1. Log in to the [dashboard](https://app.mindclade.com) and go to **Settings → API Keys**.
  2. Check whether the key's status shows **Revoked** or **Expired**.
  3. Create a new key and update every environment or secrets manager entry that references the old key.

  <Tip>
    Set up key rotation reminders in your calendar, or use a secrets manager (AWS Secrets Manager, HashiCorp Vault, etc.) that supports automatic rotation so you're never caught off guard.
  </Tip>
</Accordion>

<Accordion title="Production key used against sandbox, or vice versa">
  **Symptom:** Requests return `401` with `"code": "environment_mismatch"`. Your key appears valid, but the right resources never appear.

  **Cause:** A `mk_live_` key sent to `sandbox.api.mindclade.com/v1`, or a `mk_test_` key sent to `api.mindclade.com/v1`, will always be rejected — keys are scoped to a single environment.

  **Fix:** Match the key prefix to the base URL:

  | Key prefix | Correct base URL |
  |---|---|
  | `mk_live_` | `https://api.mindclade.com/v1` |
  | `mk_test_` | `https://sandbox.api.mindclade.com/v1` |

  If you manage both environments in the same codebase, use separate environment variables:

  ```bash
  # .env.production
  MINDCLADE_API_KEY=mk_live_abc123
  MINDCLADE_BASE_URL=https://api.mindclade.com/v1

  # .env.development
  MINDCLADE_API_KEY=mk_test_xyz789
  MINDCLADE_BASE_URL=https://sandbox.api.mindclade.com/v1
  ```
</Accordion>

## Webhooks Not Arriving

Work through this checklist in order. Each item eliminates a common failure mode.

<Steps>
  <Step title="Confirm your endpoint is publicly reachable">
    MindClade's delivery system cannot reach `localhost`, private IP ranges (`10.x.x.x`, `192.168.x.x`), or VPN-only hosts. During local development, expose your endpoint with a tunnel tool like [ngrok](https://ngrok.com) or [Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/connections/connect-networks/).

    ```bash
    # Expose local port 3000 with ngrok
    ngrok http 3000
    # Use the generated https://xxxxx.ngrok.io URL when registering the webhook
    ```
  </Step>

  <Step title="Return a 2xx status code promptly">
    MindClade marks a delivery as failed if your endpoint does not return an HTTP `2xx` status within **10 seconds**. Offload any heavy processing (database writes, downstream API calls) to a background job or queue, and immediately return `200 OK` after signature verification passes.

    ```javascript
    app.post("/webhooks/mindclade", (req, res) => {
      // Verify signature first (see FAQ)
      if (!verifySignature(secret, req.rawBody, req.headers["x-mindclade-signature"])) {
        return res.status(400).send("Invalid signature");
      }
      // ACK immediately
      res.status(200).send("OK");
      // Process asynchronously
      processEventAsync(req.body).catch(console.error);
    });
    ```
  </Step>

  <Step title="Check that signature verification isn't silently rejecting events">
    A common pitfall is verifying against a **parsed** JSON body instead of the **raw** byte buffer. JSON serializers may reorder keys or alter whitespace, producing a different byte sequence and a failed HMAC check.

    In Express, use `express.raw()` (not `express.json()`) on your webhook route:

    ```javascript
    app.post(
      "/webhooks/mindclade",
      express.raw({ type: "application/json" }),
      (req, res) => {
        // req.body is now a Buffer — pass directly to verifySignature
      }
    );
    ```
  </Step>

  <Step title="Use the dashboard webhook tester">
    In the [MindClade dashboard](https://app.mindclade.com), go to **Settings → Webhooks**, select your endpoint, and click **Send Test Event**. This fires a real `resource.created` payload to your endpoint and shows the full request/response exchange — headers, body, HTTP status, and latency — so you can pinpoint exactly where the failure occurs.

    Check the **Delivery Logs** tab for historical delivery attempts, status codes, and retry schedules for any events that failed in production.
  </Step>
</Steps>

## Rate Limit Errors (429)

When you exceed the allowed request rate, the API returns `429 Too Many Requests`. The response always includes three headers that tell you exactly when you can retry.

```http
HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit: 1000
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1717200000
```

**Reading the reset header:** `X-RateLimit-Reset` is a Unix timestamp in seconds. Subtract `Date.now() / 1000` from it to get the number of seconds you need to wait before the window resets.

**Implement exponential backoff** instead of a simple fixed delay. The example below handles both planned waits (using the reset header) and unexpected bursts (using randomised jitter):

<CodeGroup>
  ```javascript JavaScript
  async function fetchWithRetry(url, options, maxRetries = 5) {
    for (let attempt = 0; attempt <= maxRetries; attempt++) {
      const res = await fetch(url, options);

      if (res.status !== 429) return res;

      const reset = res.headers.get("X-RateLimit-Reset");
      let waitMs;

      if (reset) {
        waitMs = Math.max(0, Number(reset) * 1000 - Date.now()) + 50; // 50ms buffer
      } else {
        const base = Math.min(500 * 2 ** attempt, 30000);
        waitMs = base + Math.random() * 500; // jitter
      }

      console.warn(`Rate limited. Retrying in ${Math.round(waitMs)}ms (attempt ${attempt + 1})`);
      await new Promise((r) => setTimeout(r, waitMs));
    }
    throw new Error("Exceeded maximum retries due to rate limiting");
  }
  ```

  ```python Python
  import time, random, httpx

  def fetch_with_retry(url: str, headers: dict, max_retries: int = 5):
      for attempt in range(max_retries + 1):
          res = httpx.get(url, headers=headers)
          if res.status_code != 429:
              return res

          reset = res.headers.get("X-RateLimit-Reset")
          if reset:
              wait = max(0, int(reset) - time.time()) + 0.05
          else:
              wait = min(0.5 * (2 ** attempt), 30) + random.uniform(0, 0.5)

          print(f"Rate limited. Retrying in {wait:.1f}s (attempt {attempt + 1})")
          time.sleep(wait)

      raise RuntimeError("Exceeded maximum retries due to rate limiting")
  ```
</CodeGroup>

<Tip>
  Spread burst workloads over time by processing items in small batches with a short `sleep` between them, rather than firing all requests simultaneously.
</Tip>

## SDK Not Initializing

<Accordion title="Missing or undefined API key environment variable">
  **Symptom:** The SDK throws `MindCladeAuthError: No API key provided` or silently sends requests without an `Authorization` header.

  **Cause:** The environment variable holding your key isn't set in the current process, or it's defined in a `.env` file that isn't being loaded.

  **Fix:** Confirm the variable is set before the SDK initializes:

  ```javascript
  // Load .env early — before any imports that touch the SDK
  require("dotenv").config();
  const MindClade = require("@mindclade/sdk");

  if (!process.env.MINDCLADE_API_KEY) {
    throw new Error("MINDCLADE_API_KEY is not set");
  }

  const client = new MindClade({ apiKey: process.env.MINDCLADE_API_KEY });
  ```
</Accordion>

<Accordion title="Wrong import style (CommonJS vs. ESM)">
  **Symptom:** `Cannot find module`, `SyntaxError: The requested module does not provide an export named 'default'`, or `MindClade is not a constructor`.

  **Cause:** Mixing CommonJS `require()` with ESM `import`, or the reverse.

  **Fix:** Use the import style that matches your project's module system:

  ```javascript
  // ESM (package.json "type": "module" or .mjs files)
  import MindClade from "@mindclade/sdk";

  // CommonJS (.cjs or no "type" field in package.json)
  const MindClade = require("@mindclade/sdk").default;
  // — or, for named exports —
  const { MindClade } = require("@mindclade/sdk");
  ```
</Accordion>

<Accordion title="Unsupported Node.js version">
  **Symptom:** Syntax errors or feature-not-found crashes on startup, even though the package installed successfully.

  **Cause:** `@mindclade/sdk` requires **Node.js 18 or later** for native `fetch` and `crypto.subtle` support.

  **Fix:** Check your Node version and upgrade if necessary:

  ```bash
  node --version   # should be >= 18.0.0

  # Upgrade with nvm
  nvm install 20
  nvm use 20
  ```

  If you're on an older LTS version in CI or production, update your `.nvmrc` or Docker base image accordingly.
</Accordion>

## Pagination Issues

<Accordion title="Reusing an expired cursor">
  **Symptom:** A request mid-pagination returns `400 Bad Request` with `"code": "invalid_cursor"` even though the cursor came directly from a previous response.

  **Cause:** Cursors are valid for **15 minutes** from the time they're issued. If your pagination loop pauses for longer than that — for example, due to slow processing of each page or a background-job queue delay — the cursor expires before you use it.

  **Fix:** Don't store cursors for later use. Process each page immediately and request the next one before the cursor expires:

  ```javascript
  // ✅ Fetch all pages in a single continuous loop
  let cursor = undefined;
  const results = [];

  do {
    const page = await client.resources.list({
      limit: 100,
      ...(cursor && { cursor }),
    });
    results.push(...page.data);
    cursor = page.next_cursor;
  } while (page.has_more);
  ```

  If you must process large datasets across multiple jobs, use a filter (such as `created_after` with a timestamp) to restart from a known stable point rather than relying on a saved cursor.
</Accordion>
