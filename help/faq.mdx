<Accordion title="How do I get an API key?">
  Log in to the [MindClade dashboard](https://app.mindclade.com) and navigate to **Settings → API Keys**. Click **Create Key**, give it a descriptive name (for example, `my-app-production`), and choose whether it should target the **sandbox** or **production** environment. Your key is shown only once — copy it immediately and store it in a secure secrets manager or environment variable.

  Production keys are prefixed `mk_live_` and sandbox keys are prefixed `mk_test_`. Never commit either type to source control.

  ```bash
  # Example: pass your key in every request
  curl https://api.mindclade.com/v1/resources \
    -H "Authorization: Bearer mk_live_abc123xyz"
  ```
</Accordion>

<Accordion title="What's the difference between sandbox and production?">
  MindClade provides two fully isolated environments:

  | | Sandbox | Production |
  |---|---|---|
  | **Base URL** | `https://sandbox.api.mindclade.com/v1` | `https://api.mindclade.com/v1` |
  | **Key prefix** | `mk_test_` | `mk_live_` |
  | **Rate limit** | 100 req/min | 1 000 req/min |
  | **Data** | Isolated — no real data | Live data |

  Use the sandbox environment during development and CI/CD pipelines so you can create, update, and delete resources without affecting live data. Data created in the sandbox never crosses over to production.

  <Warning>
    A `mk_test_` key will be rejected by the production endpoint and vice versa. Make sure the key prefix matches the base URL you're targeting.
  </Warning>
</Accordion>

<Accordion title="How do I handle rate limits?">
  Every API response includes three headers that tell you exactly where you stand:

  - `X-RateLimit-Limit` — the total requests allowed in the current window (1 000 for production, 100 for sandbox)
  - `X-RateLimit-Remaining` — how many requests you have left in the current window
  - `X-RateLimit-Reset` — Unix timestamp (seconds) when the window resets

  When you exceed the limit, the API returns `429 Too Many Requests`. Read the `X-RateLimit-Reset` header, wait until that timestamp, and then retry. For best results, implement exponential backoff with jitter rather than hammering the endpoint at the reset moment.

  ```javascript
  async function requestWithBackoff(fn, retries = 4) {
    for (let attempt = 0; attempt <= retries; attempt++) {
      const res = await fn();
      if (res.status !== 429) return res;
      const reset = res.headers.get("X-RateLimit-Reset");
      const delay = reset
        ? Math.max(0, Number(reset) * 1000 - Date.now())
        : Math.min(1000 * 2 ** attempt + Math.random() * 500, 30000);
      await new Promise((r) => setTimeout(r, delay));
    }
    throw new Error("Rate limit retries exhausted");
  }
  ```

  <Tip>
    Batch writes using `PATCH /resources/{id}` in parallel rather than making sequential single-field updates to stay well under the limit.
  </Tip>
</Accordion>

<Accordion title="Can I use MindClade in a browser (client-side)?">
  We strongly recommend against calling the MindClade API directly from browser JavaScript. Doing so would expose your `mk_live_` or `mk_test_` key to anyone who inspects network traffic or your bundle.

  The correct pattern is to proxy requests through your own backend:

  1. Your frontend calls **your** backend endpoint (e.g., `POST /api/resources`).
  2. Your backend authenticates the user with your own auth system.
  3. Your backend calls `https://api.mindclade.com/v1/resources` using the key stored in a server-side environment variable.
  4. Your backend returns only the data your frontend needs.

  If you genuinely need client-side access (for example, in a serverless edge function), scope the key to the minimum required permissions and rotate it regularly from the dashboard.
</Accordion>

<Accordion title="How do I verify webhook signatures?">
  MindClade signs every webhook payload with HMAC-SHA256. The signature is sent in the `X-MindClade-Signature` header as a hex digest.

  To verify it, compute `HMAC-SHA256(secret, rawRequestBody)` using the signing secret shown in **Settings → Webhooks** for your endpoint, then compare the result to the header value. Always compare the raw request body bytes — not a parsed JSON object — and use a constant-time comparison to prevent timing attacks.

  <CodeGroup>
    ```javascript Node.js
    const crypto = require("crypto");

    function verifySignature(secret, rawBody, signatureHeader) {
      const expected = crypto
        .createHmac("sha256", secret)
        .update(rawBody)
        .digest("hex");
      const trusted = Buffer.from(expected, "hex");
      const received = Buffer.from(signatureHeader, "hex");
      if (trusted.length !== received.length) return false;
      return crypto.timingSafeEqual(trusted, received);
    }
    ```

    ```python Python
    import hashlib, hmac

    def verify_signature(secret: str, raw_body: bytes, signature_header: str) -> bool:
        expected = hmac.new(
            secret.encode(), raw_body, hashlib.sha256
        ).hexdigest()
        return hmac.compare_digest(expected, signature_header)
    ```
  </CodeGroup>

  Return a `200` response only after the signature passes. Return `400` and discard the payload if verification fails.
</Accordion>

<Accordion title="What happens if my webhook endpoint is down?">
  MindClade retries failed webhook deliveries automatically using exponential backoff. A delivery is considered failed if your endpoint:

  - Returns a non-`2xx` HTTP status code
  - Does not respond within **10 seconds**
  - Is unreachable (DNS failure, connection refused, etc.)

  The retry schedule is roughly: **immediately → 30 s → 2 min → 10 min → 1 h → 6 h → 24 h**. After all retries are exhausted (approximately 72 hours), the delivery is marked as **failed** and no further attempts are made.

  You can inspect the full delivery log — including request bodies, response codes, and retry history — in the [dashboard](https://app.mindclade.com) under **Settings → Webhooks → Delivery Logs**.

  <Note>
    If you recover your endpoint before retries are exhausted, the next scheduled retry will succeed automatically — no manual action is required.
  </Note>
</Accordion>

<Accordion title="Are there SDK type definitions for TypeScript?">
  Yes. The `@mindclade/sdk` npm package ships full TypeScript type definitions out of the box — no `@types/` package required. Every request option, response object, and error type is strongly typed.

  ```typescript
  import MindClade, { Resource, ListResponse } from "@mindclade/sdk";

  const client = new MindClade({ apiKey: process.env.MINDCLADE_API_KEY! });

  const result: ListResponse<Resource> = await client.resources.list({ limit: 25 });
  result.data.forEach((r: Resource) => console.log(r.id, r.metadata));
  ```

  The SDK also exports utility types like `CreateResourceParams`, `UpdateResourceParams`, and the full `MindCladeError` hierarchy so you can type your own wrapper functions precisely.
</Accordion>

<Accordion title="How do I paginate through large lists?">
  MindClade uses **cursor-based pagination** on all list endpoints. The initial request returns a `next_cursor` string and a `has_more` boolean alongside the `data` array.

  Pass `next_cursor` as the `cursor` query parameter on your next request to fetch the following page. Keep iterating until `has_more` is `false`.

  ```javascript
  let cursor = undefined;
  const allResources = [];

  do {
    const params = { limit: 100, ...(cursor && { cursor }) };
    const page = await client.resources.list(params);
    allResources.push(...page.data);
    cursor = page.next_cursor;
  } while (page.has_more);

  console.log(`Fetched ${allResources.length} resources`);
  ```

  <Warning>
    Cursors are time-bound and expire after **15 minutes**. Do not store a cursor and resume pagination hours later — restart from the beginning instead.
  </Warning>
</Accordion>

<Accordion title="What regions is MindClade available in?">
  The MindClade API is served from a globally distributed edge network, so your requests are automatically routed to the nearest point of presence for low-latency responses worldwide.

  All data at rest is stored in the region you select when creating your organization (US, EU, or APAC). Data does not leave your selected region, which helps with GDPR and data-residency requirements.

  You can view the current region assignment for your organization in **Settings → Organization → Region**.
</Accordion>
