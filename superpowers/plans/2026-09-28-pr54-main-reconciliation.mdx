## 4. Execution Sequence

### Phase A: Freeze and Document

1. Confirm protected `main`, record the live PR head, and if main advanced from the owner-supplied base, verify the new main is already an ancestor or perform a new bounded overlap assessment before continuing.
2. Write this plan and update the durable repository blueprints before further CI qualification.
3. Update dated status/handoff documents so a new agent can distinguish:
   - PR-bound R2 prerequisite evidence,
   - exact-candidate/resulting-main R2 evidence,
   - the managed-runner replacement path,
   - required fresh review/checks after a head change.

**Exit:** documentation is internally consistent and does not claim acceptance.

### Phase B: Reconcile Source

1. Merge the named protected base into the PR branch without force-pushing.
2. Resolve only genuine overlaps from the conflict map.
3. Preserve all non-overlapping files from both histories.
4. Regenerate `REPOSITORY_TREE.md` mechanically after all tracked-path changes.
5. Run `git diff --check` and inspect the PR-to-main file list for accidental additions/removals.

**Exit:** branch is a descendant of both the original PR head and protected base; no conflict markers, stale tree or unrelated source changes remain.

### Phase C: Focused Source Verification

Run, at minimum:

```bash
python3 scripts/test_ci_policy.py
python3 scripts/test_r2_runner_canary_policy.py
python3 scripts/test_postgres_substrate_policy.py
python3 scripts/test_r2_diagnostic.py
python3 scripts/test_governance_binding.py

git diff --check
```

Any changed documentation that adds/removes paths requires a fresh tree regeneration before the final verification pass.

**Exit:** all focused checks pass on the exact source head to be pushed.

### Phase D: Publish Refreshed Head and Exact-Head CI

1. Fetch the remote PR branch immediately before push.
2. Abort rather than overwrite if a concurrent remote head is not an ancestor of the local candidate.
3. Push the normal fast-forward successor using `robpearc@mindclade.com` commit identity.
4. Treat every approval and CI result from an older head as stale for admission.
5. Observe the new `Executable Foundation` pull-request run.
6. Require both:
   - `Linux sandbox prerequisite` SUCCESS with semantic R2 PASS, and
   - protected `linux-foundation` SUCCESS on the refreshed exact candidate.
7. Inspect retained R2 evidence/result, not only the job conclusion.

**Exit:** exact-head required CI is green and semantically valid.

### Phase E: Readiness Assessment Only

After Phase D, report merge-queue readiness. Do **not** approve, enqueue or merge.

Ready for human approval/queue admission requires all of:

- PR is Git-mergeable against the current protected base.
- Required exact-head `linux-foundation` is green.
- R2 prerequisite receipt is semantically PASS.
- No unresolved review threads or source-policy failures remain.
- Prior CODEOWNER approval is not counted after the head refresh.
- A fresh CODEOWNER approval is still required.
- Queue admission remains a separate human action and will create a new synthetic merge-group identity requiring its own required check.
- Resulting-main evidence remains future evidence until an authorized merge occurs.

If `main` advances again before queue admission, repeat the delta/conflict assessment and invalidate affected exact-head evidence as required by repository policy.

## 5. Stop Conditions

Stop and report rather than paper over any of the following:

- protected `main` changes beyond the assessed base in a way that overlaps the PR;
- the remote PR head advances concurrently with non-ancestor changes;
- Ubuntu 22.04 no longer exposes the required `linux-sandbox`;
- `linux-foundation` is skipped or made non-required instead of failing closed;
- action pins, permissions, branch protection, queue rules or security settings would need relaxation;
- the R2 receipt is missing, BLOCKED or FAIL even if a surrounding job appears green;
- repository-tree regeneration introduces unexplained paths;
- a requested action would constitute approval, queue admission or merge without a fresh human decision.

## 6. Completion Record

The final reconciliation report must name:

- protected base and refreshed PR head;
- exact changed-file set versus main;
- focused local/source check results;
- exact GitHub Actions run and job conclusions;
- retained R2 semantic status and artifact reference when available;
- Git mergeability and ruleset-required context state;
- review state, explicitly identifying stale vs fresh CODEOWNER approval;
- one of: **ready for fresh human approval/queue admission**, **BLOCKED**, or **requires another current-main reconciliation**.

This plan intentionally stops before approval or merge.
