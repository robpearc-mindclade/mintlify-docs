## 1. Scope, non-goals and the guarantee

**In scope:**

- an isolated, real PostgreSQL provided by Nix;
- a checksum-bound schema;
- atomic admission with a transactional outbox;
- canonical idempotency;
- at-least-once dispatch with inbox deduplication;
- generations and leases timed by the database;
- fenced completion;
- crash/restart recovery;
- bounded retries;
- confirmed cancellation;
- the generated TypeScript client driving the real HTTP → PostgreSQL → worker path.

All of it must hold on Apple Silicon (`aarch64-darwin`) and Linux (`x86_64-linux`).

**The guarantee C proves:**

- delivery is at least once;
- each Run has at most one authoritative completion;
- every admitted Run reaches a terminal state (`succeeded`, `failed` or `cancelled`) within three attempts, once a live worker runs reconciliation. A Run that stays non-terminal past the harness deadline fails the test.

This holds across two fault classes:

- process crashes: SIGKILL of the service, worker or recovery child;
- PostgreSQL crash restarts: `pg_ctl stop -m immediate`, followed by WAL crash recovery.

It does **not** cover power loss or an operating-system crash. On macOS, PostgreSQL's `fsync` path does not force the drive's write cache the way `fsync_writethrough` (F_FULLFSYNC) does. C records `SHOW wal_sync_method` on both hosts (C1-06) and makes no power-loss claim. Whether to claim more is Rob's decision (Section 13 item 12).

**Out of scope.** Each of these is rejected at review if it appears:

- a public async, 202, poll or cancel endpoint;
- a message broker, Temporal, Kubernetes, Docker, SQLite or any other in-memory "durable" store;
- any cloud or deployment work;
- production credentials, passwords, TLS, or a TCP listener for PostgreSQL (OD-4);
- external effect providers, or any real NOVA or scientific work;
- replay, capsule sealing or assessment (these are D1–D4);
- moving slice behaviour into `platform/persistence`, `platform/scheduler`, `services/scheduler`, `services/workers` or `tools/migrations` (OD-3);
- Intel Mac qualification.

HTTP timeout or client disconnect is **not** cancellation. The success response keeps status 200 and the exact Echo body.

### OD-4 Test-only trust authentication and database roles

**Common to both options:**

- `listen_addresses = ''`;

**Roles (finding I8):**

- **(b)** Two trust roles:
  - `mindclade_admin`, a superuser that runs the migration and owns every table;

**How the roles are created (Minor N5):**

- `initdb -U mindclade_admin` makes the bootstrap superuser `mindclade_admin`, under both options. No `postgres` role and no OS-user role exist.
- `PgHarness` is std-only TestKit and has no database driver. B3b-26 pins TestKit's normal dependencies to exactly `{core, runtimekit}`. So the harness creates roles and the database **without a client connection**, in single-user mode, after `initdb` and before `pg_ctl start`:
  - It runs `postgres --single -j -D <data> postgres` through `MINDCLADE_POSTGRES_BIN`, with `env_clear()`, the harness deadline, and statements supplied on stdin.
  - Under both options it runs `CREATE DATABASE mindclade OWNER mindclade_admin`.
  - Under (b) it also runs `CREATE ROLE mindclade_app LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION NOBYPASSRLS`.
  - A non-zero exit returns `TestError::CommandFailure`, and nothing starts.
- The migration, run as `mindclade_admin`, creates the tables and grants `mindclade_app` only the privileges listed above.

   - **(i) Tamper helpers** commit. Each runs with `session_replication_role = replica`: `expire_lease`, `set_retry_eligible_now`, `corrupt_artifact_bytes`, `corrupt_reference_kind`, `set_migration_checksum_byte`, `set_persisted_version`, `set_run_state_without_event`.

     `session_replication_role = replica`: `expire_lease`, `set_retry_eligible_now`, `corrupt_artifact_bytes`, `corrupt_reference_kind`, `set_migration_checksum_byte`, `set_persisted_version`, `set_run_state_without_event`.
   - **(ii) Lock helpers** (N2) **always roll back** and never commit.
     - The read-only observer cannot take these locks: PostgreSQL rejects `LOCK TABLE … IN SHARE MODE` and `FOR UPDATE` in a read-only transaction.

     - `lock_artifacts_share()`: `LOCK TABLE artifacts IN SHARE MODE`.

4. **`BarrierCheckpoints`**, built on `FaultBarrier`.
5. **`FakeWorker::compute(&Lease, &EchoRequest) -> Completion`**, a counting wrapper around `execution::worker::compute_echo_artifact` (N3).
6. **`RecoveryHarness`.** It:
   - spawns `recovery_child` in a mode;
   - waits for the child's `checkpoint <name>` line;
   - sends `continue`, or kills the child and records its exit status through `Engine::record_exit_observation`, as the production supervisor would;
   - calls `crash_restart`.
7. **`recovery_child`.** Takes its DSN over stdin, calls only the §4.2 `Engine` entrypoints, and contains no SQL. Its modes are `admit`, `work`, `work --until-terminal`, `cancel` (calls `request_cancel`) and `confirm` (calls `reconcile_once`, which calls `confirm_cancel`).

**Observation SQL and case scripts** are reserved to the test author (§5.4): `tests/observe.rs` (every `snapshot` query and invariant) and `tests/recovery_cases.rs` (the steps and expected table for every case, including the plan's `run_recovery_case`).

**Why a separate crate:**

- **Not `cfg(test)`.** It compiles only into the crate's own unit-test binary. The reserved integration tests and child processes link the non-test build, so they could not reach the hooks.
- **Not a Cargo feature.** B4 collects `--all-features`. Two Bazel variants of one crate have types that do not unify. And production would run code that differs from the tested variant.
- **What the trait gives.** Identical store code runs in tests and in production. Reachability is enforced by Bazel `testonly`, by B4 `production-to-test`, and by the `binary_deps` genquery (C5-09).

**Unit tests.** In-crate unit tests in `services/foundation_echo/src/**` never use the testing crate or PostgreSQL. Bazel would link two instances of the library.

## 6. Acceptance criteria

The format follows B3b: each criterion gives a positive control (P), negative cases (N) and a Bazel target.

Rules that apply to every criterion:

- **Every negative has a positive control.** A store that rejects everything must not pass.
- **Negatives name their error.** Each negative names the exact `StoreError` or `TestError` variant, or the exact B4 diagnostic (Minor).
- **Observation is independent.** Durable assertions are observed on real PostgreSQL through the reserved `observe.rs` queries on an independent read-only session. Method return values alone are never enough.
- **No skips.** "Fails" means a non-passing Bazel test, never a skip, `#[ignore]` or early return.
- **Timeouts are failures.** Harness deadlines fail with a distinct "harness timeout" message, and such a timeout is never product success.
- **Races must overlap (finding I7).** Wherever a criterion says _overlap observed_, the test must see, before releasing the first party, that the second party's backend is waiting on a lock or is inside the contested window, and must record that observation. It identifies the backend by `application_name` in `pg_stat_activity`. Waiting means `wait_event_type = 'Lock'` with a matching ungranted `pg_locks` row; being inside the window means `state = 'idle in transaction'` at a named checkpoint. A race that ran sequentially fails. The waiting loop is deadline-bounded, is paced by `recv_timeout` of a few milliseconds on a channel that never receives (residual a), and never calls `sleep`.

### C1: Harness and schema

**C1-01 Owned, Unix-socket-only cluster.**

- P:
  - `PgHarness::start` creates, through `mkdtemp`, a data directory and a short socket directory. Both have mode 0700 and are owned by the test user.
  - The socket path is at most 103 bytes.
  - `SHOW listen_addresses` is `''`, and `SHOW unix_socket_directories` equals the owned directory.
  - The postmaster PID owns no TCP listening socket. On Linux this is checked through `/proc/&lt;pid&gt;/net/tcp{,6}` plus `/proc/&lt;pid&gt;/fd` inodes; on macOS through `/usr/sbin/lsof -nP -a -p &lt;pid&gt; -iTCP -sTCP:LISTEN`. The check is scoped to the PID, so a host service on 5432 cannot make it flaky (finding I14).
- N:

## 6. Acceptance criteria

The format follows B3b: each criterion gives a positive control (P), negative cases (N) and a Bazel target.

Rules that apply to every criterion:

- **Every negative has a positive control.** A store that rejects everything must not pass.
- **Negatives name their error.** Each negative names the exact `StoreError` or `TestError` variant, or the exact B4 diagnostic (Minor).
- **Observation is independent.** Durable assertions are observed on real PostgreSQL through the reserved `observe.rs` queries on an independent read-only session. Method return values alone are never enough.
- **No skips.** "Fails" means a non-passing Bazel test, never a skip, `#[ignore]` or early return.
- **Timeouts are failures.** Harness deadlines fail with a distinct "harness timeout" message, and such a timeout is never product success.
- **Races must overlap (finding I7).** Wherever a criterion says _overlap observed_, the test must see, before releasing the first party, that the second party's backend is waiting on a lock or is inside the contested window, and must record that observation. It identifies the backend by `application_name` in `pg_stat_activity`. Waiting means `wait_event_type = 'Lock'` with a matching ungranted `pg_locks` row; being inside the window means `state = 'idle in transaction'` at a named checkpoint. A race that ran sequentially fails. The waiting loop is deadline-bounded, is paced by `recv_timeout` of a few milliseconds on a channel that never receives (residual a), and never calls `sleep`.

### 6.1 C1: PostgreSQL harness, schema and settings

**C1-01: Socket-only, no TCP.** The harness starts `initdb` and `pg_ctl start` with `listen_addresses = ''`, using a socket in a short directory with mode 0700. On macOS, `lsof -nP -a -p <postmaster pid> -iTCP -sTCP:LISTEN` inside the Bazel test action returns no lines. On Linux, `/proc/<postmaster pid>/net/tcp` shows no listening sockets.

**C1-02: Runfile env keys required.** Under Bazel, each PostgreSQL test fails fast with a clear error if any of `MINDCLADE_POSTGRES_BIN`, `MINDCLADE_INITDB_BIN`, `MINDCLADE_PG_CTL_BIN`, or `MINDCLADE_PG_CONTROLDATA_BIN` is missing. Under Cargo (which has no runfiles), these tests are not compiled or run (Section 4.2).

**C1-03: DSN keys restricted.** `PgStore::connect` rejects a DSN whose key set is not exactly `{host, user, dbname, application_name}`. `connect_with` takes the same DSN restriction. No TCP port, password or SSL parameter is accepted. The `host` value must be a socket directory path.

**C1-04: All binaries from one Nix store path.** After canonicalising the four env values, they all lie in the same `/nix/store/…/bin` directory.

**C1-05: Tool env cleared.** Every child process spawned by `PgHarness` starts with `env_clear()` and an explicit allowlist of at most `{PATH, HOME, TMPDIR}`.

**C1-06: Durability settings checked every session.** `verify_durability` runs on every new store connection and checks every required setting. The check records `wal_sync_method`. The list of checked settings is in a reserved scan (C5-09). The session's `rolsuper` is recorded; under OD-4(b) it must be `false`.

**C1-07: Advisory key pre-created.** Before the migration runs, `PgHarness` creates an empty table `runs` with a unique index on `(admission_key)`. The migration then adds the remaining columns. This proves that the admission key constraint is a persistent index, not a session-level check.

**C1-08: Schema version persisted and rejected.** A `store_version` table holds a single row with the schema checksum. `verify_durability` rejects a connection whose `store_version` row does not match the in-code checksum. A tamper helper `set_persisted_version` changes the stored checksum; the next `verify_durability` on a new connection returns `IncompatibleVersion`.

**C1-09: Append-only enforced.** `durable_boundaries.rs` contains a reserved scan that checks `services/foundation_echo/src/execution/store.rs` for `DELETE` or `UPDATE` on `runs`, `outbox`, `artifacts`, `attempts` or `events`. Only the updates listed in C1-13 are allowed. The scan also checks for `ALTER TABLE … DISABLE TRIGGER` or `ALTER SYSTEM`. Any disallowed pattern fails the test.

**C1-10: WAL crash recovery observed.** `crash_restart` runs `pg_ctl stop -m immediate`, checks `pg_controldata` for a state other than `shut down`, then starts again. The next store connection succeeds and `verify_durability` passes.

**C1-11: Query timeout.** A store query that exceeds the deadline returns `StoreError::Database` with a clear timeout indicator. The timeout is set on the connection or statement, not by a client-side sleep.

**C1-12: DSN redaction.** The DSN logged by `PgStore` (telemetry or debug) omits the `user` value and shows `host=<redacted>`. The full DSN is never printed.

**C1-13: Immutable columns.** A tamper helper that `UPDATE`s a disallowed column on `runs`, `outbox`, `artifacts`, `attempts` or `events` returns `StoreError::Integrity` when the store next reads that row. The allowed column updates are: `lease` (only the worker claim and expiry), `outbox.pending`, `attempts.result`, and `events.observation`.

### 6.2 C2: Admission

**C2-01: Atomic admission with outbox.** Admitting a Run with a new `request_id` inserts exactly one row into `runs` and at least one row into `outbox`, within one transaction. If the transaction commits, both are durable. If it rolls back, neither is present.

**C2-02: Identity in admission key.** The `AdmissionContext` identity and the `WorkPacket.capability` form the admission key. A duplicate admission key with the same identity and capability returns `Existing(RunRef)`.

**C2-03: Idempotency returns the same RunRef.** Repeating an admission with the same `request_id` returns the same `RunRef` and `RunState`.

**C2-04: Conflict on different capability.** Admitting the same `request_id` with a different `WorkPacket.capability` returns `Conflict`.

**C2-05: Concurrent admission races win or block.** Two `admit` calls with the same new `request_id` and `BarrierCheckpoints` at `AfterRunInsertBeforeOutbox` and `BeforeAdmissionCommit` produce exactly one `Created` and one `Existing`. No double insert occurs.

**C2-06: Paused or terminal migrates or fails.** If a Run is already terminal (`succeeded`, `failed`, `cancelled`) or the worker policy rejects it as paused, `admit` returns the existing `RunRef` and the current state. It does not create a new Run.

### 6.3 C3: Dispatch, claim and complete

**C3-01: One outbox row per admitted Run.** Every admitted Run produces exactly one `outbox` row with `pending = true`. A duplicate admission returns the same `RunRef` and produces no new outbox row.

**C3-02: Batch dispatch in order.** `dispatch_batch(limit)` returns up to `limit` outbox rows, ordered by `created_at`. Each returned row has `pending = true`. The rows are locked with `FOR UPDATE SKIP LOCKED`.

**C3-03: Claim with generation lease.** `claim(identity)` atomically finds the oldest pending dispatch, inserts or updates a `lease` row with generation `1`, sets `expires_at` to `now + lease_duration`, and returns the `Lease`. A second concurrent claim on the same Run returns `None` because the lease row is locked.

**C3-04: Fenced completion.** `complete(&Completion)` checks the lease generation: if the `Lease` generation does not match the `Run`'s current generation, it returns `StaleLease`. If it matches, it inserts an `artifact` row and transitions the `Run` to `succeeded` in one transaction. A second `complete` with the same or later generation returns `AlreadyCommitted(ArtifactRef)`.

**C3-05: Dispatch after failure re-enters outbox.** When `record_failure` is called with `FaultClass::Transient`, the Run transitions to `retrying`, the generation increments, and the outbox row is reset to `pending = true` with a new `retry_eligible_at` based on the delay schedule (OD-5). `dispatch_batch` will re-return it.

**C3-06: Same bytes for same input.** For the same `(lease, request)`, `FakeWorker::compute` and a production `work_once` store equal bytes in the committed artifact. The test compares the artifact SHA-256 from both paths.

**C3-07: Deterministic retry schedule.** The retry delays are 100 ms and 500 ms. After two transient failures, the Run transitions to `failed` and the outbox row is not reset.

### 6.4 C4: Recovery, cancel and liveness

**C4-01: Reconcile retries to terminal.** A Run in `retrying` with `retry_eligible_at <= now` is reclaimed by `reconcile()`, given a new lease, and re-dispatched. After three attempts total (the original plus two retries), it transitions to `failed` if still not completed.

**C4-02: Cancel with observation.** `request_cancel(CancelRequest)` transitions the Run to `cancelling` if it is not terminal. `confirm_cancel(CancelConfirmation)` checks `termination_observation`: if it matches the SHA-256 of the recorded `ExitObservation`, the Run transitions to `cancelled`. If the observation does not match, it returns `Pending`. If the Run is already terminal, it returns `AlreadyTerminal`.

**C4-03: Record failure on lease timeout.** If a worker does not complete within the lease duration, `reconcile()` records `FaultClass::Transient`, expires the lease, and re-enters the Run into the outbox (subject to the retry limit).

**C4-04: Tamper detection.** A tamper helper that corrupts a row returns `StoreError::Integrity` on the next store read. The tamper methods are exactly those in Section 4.3.

**C4-05: Liveness across crash/restart.** The scenario cases in `recovery_cases.rs` are run with the process harness. Each case is run 20 times. The flakiness budget is: zero flakes allowed at 20 runs if p \< 0.01, else one flake allowed if p \< 0.05.

The liveness cases are:

| Case | Steps | Expected terminal state |
| --- | --- | --- |
| A1 | Admit, crash service mid-dispatch, restart, reconcile | `succeeded` |
| A2 | Admit, crash worker mid-compute, restart, reconcile | `succeeded` |
| A3 | Admit, complete, crash before ack, restart | `succeeded` (already committed) |
| B1 | Admit, request cancel, crash service before confirm, record exit observation, restart, reconcile | `cancelled` |
| B2 | Admit, dispatch, claim, record failure, crash, restart, reconcile | `failed` (after 3 attempts) or `succeeded` (if a later claim wins) |
| B3 | Admit, crash PostgreSQL mid-transaction, crash_restart, reconnect, reconcile | `succeeded` (if commit made it to WAL) or `retrying` (if not) |
| X1 | Admit with all checkpoints held, inject faults at every checkpoint, release randomly, verify no deadlock | all runs terminal |
| X2 | Stress: 50 concurrent admissions, random crashes, reconcile, verify every run terminal within deadline | all runs terminal |

**C4-06: Budget for the ×50 runs.** The admission and dispatch repeats (K6) must complete within a wall-clock budget recorded by the parent. The recommended budget is 5 minutes for the ×50 admission run and 5 minutes for the ×50 dispatch run, on the CI host with parallelism capped by P-PG3.

### 6.5 C5: End-to-end public durable tests

**C5-01: Durable descriptor and config.** The descriptor contains `dependencies.postgres.required: true`, `configuration.admission: durable`, and a durable readiness value. `AdmissionMode::Durable` exists and the ready receipt contains `"admission":"durable"`. A `ServiceConfig::new` with a dependency argument compiles. A config without the dependency argument does not compile in a durable doctest (compile-fail pair).

**C5-02: Readiness probe with locked admission key.** The public test sends requests while a lock helper holds the admission key. The readiness probe still returns ready. The public test then observes that only one request is admitted; subsequent requests with the same key return the same RunRef.

**C5-03: Close is not cancel.** Closing the client connection does not transition any Run to `cancelled`. A later reconnect and status check shows the Run is still `retrying` or `succeeded`, depending on timing.

**C5-04: Cancel is confirmed, not immediate.** A cancel request through the test helper returns a `CancelResult::Pending`. The Run transitions to `cancelled` only after `confirm_cancel` with a matching `termination_observation`.

**C5-05: Pinned target list.** `verify_vs001.py` checks that the exact target list from Section 8 matches the Bazel query output. No extra test targets are added without an update to the criteria.

**C5-06: Integration test list.** The MJS case driver runs all cases in `recovery_cases.rs` through the public HTTP → PostgreSQL → worker path. Each case produces the same terminal state as the store-level version.

**C5-07: Cycle-free, exact edge checks.** The `testing` crate is a Cargo member with `publish = false` and workspace lints. It has no production dependency on `foundation_echo_lib` (the normal edge is test-only). The negative check is a six-step scratch procedure: create a new Cargo workspace, add the testing crate as a path dependency, attempt `cargo build`, and verify it fails with a message about a missing `foundation_echo_lib` production dependency. The exact error text is recorded by the parent.

**C5-08: No TCP in public tests.** The public test MJS driver checks `SHOW listen_addresses` through the store observer and confirms it is `''`.

**C5-09: Reserved scans.** The `durable_boundaries.rs` reserved file contains scans for:

- no `sleep(` in C source (TestKit, Echo `src`, `tests`, testing crate);
- no `unsafe` in C source (except the known `postgres` crate block);
- the exact DSN key allowlist (C1-03);
- the exact durability settings list (C1-06);
- no `as_any` or `dyn Any` downcasts in C source (residual b);
- public items only in generated modules (compile-fail pairs for `generated_service_http` and `generated_service_config`).

**C5-10: Lock waiter observed.** A public test sends a request while a tamper helper holds the admission key. The test confirms that the request is queued (not rejected) and that a telemetry or log entry records the wait.

**C5-11: Worker call counts match.** The telemetry sink records exactly as many `compute_echo_artifact` calls as the store records completed attempts. The counts are compared after the scenario run.

**C5-12: Connection bound enforced.** The store uses at most `B` concurrent connections, where `B` is the bound from the durable profile (OD-6 item 4). A test that launches `B + 1` concurrent admissions observes that the `B + 1`th blocks until a connection is released. The bound is enforced by the connection pool, not by a semaphore in the store code.

**C2-05: Concurrent admission races win or block.** Two `admit` calls with the same new `request_id` and `BarrierCheckpoints` at `AfterRunInsertBeforeOutbox` and `BeforeAdmissionCommit` produce exactly one `Created` and one `Existing`. No double insert occurs.

**C2-06: Paused or terminal migrates or fails.** If a Run is already terminal (`succeeded`, `failed`, `cancelled`) or the worker policy rejects it as paused, `admit` returns the existing `RunRef` and the current state. It does not create a new Run.

### 6.3 C3: Dispatch, claim and complete

**C3-01: One outbox row per admitted Run.** Every admitted Run produces exactly one `outbox` row with `pending = true`. A duplicate admission returns the same `RunRef` and produces no new outbox row.

**C3-02: Batch dispatch in order.** `dispatch_batch(limit)` returns up to `limit` outbox rows, ordered by `created_at`. Each returned row has `pending = true`. The rows are locked with `FOR UPDATE SKIP LOCKED`.

**C3-03: Claim with generation lease.** `claim(identity)` atomically finds the oldest pending dispatch, inserts or updates a `lease` row with generation `1`, sets `expires_at` to `now + lease_duration`, and returns the `Lease`. A second concurrent claim on the same Run returns `None` because the lease row is locked.

**C3-04: Fenced completion.** `complete(&Completion)` checks the lease generation: if the `Lease` generation does not match the `Run`'s current generation, it returns `StaleLease`. If it matches, it inserts an `artifact` row and transitions the `Run` to `succeeded` in one transaction. A second `complete` with the same or later generation returns `AlreadyCommitted(ArtifactRef)`.

**C3-05: Dispatch after failure re-enters outbox.** When `record_failure` is called with `FaultClass::Transient`, the Run transitions to `retrying`, the generation increments, and the outbox row is reset to `pending = true` with a new `retry_eligible_at` based on the delay schedule (OD-5). `dispatch_batch` will re-return it.

**C3-06: Same bytes for same input.** For the same `(lease, request)`, `FakeWorker::compute` and a production `work_once` store equal bytes in the committed artifact. The test compares the artifact SHA-256 from both paths.

**C3-07: Deterministic retry schedule.** The retry delays are 100 ms and 500 ms. After two transient failures, the Run transitions to `failed` and the outbox row is not reset.

### 6.4 C4: Recovery, cancel and liveness

**C4-01: Reconcile retries to terminal.** A Run in `retrying` with `retry_eligible_at <= now` is reclaimed by `reconcile()`, given a new lease, and re-dispatched. After three attempts total (the original plus two retries), it transitions to `failed` if still not completed.

**C4-02: Cancel with observation.** `request_cancel(CancelRequest)` transitions the Run to `cancelling` if it is not terminal. `confirm_cancel(CancelConfirmation)` checks `termination_observation`: if it matches the SHA-256 of the recorded `ExitObservation`, the Run transitions to `cancelled`. If the observation does not match, it returns `Pending`. If the Run is already terminal, it returns `AlreadyTerminal`.

**C4-03: Record failure on lease timeout.** If a worker does not complete within the lease duration, `reconcile()` records `FaultClass::Transient`, expires the lease, and re-enters the Run into the outbox (subject to the retry limit).

**C4-04: Tamper detection.** A tamper helper that corrupts a row returns `StoreError::Integrity` on the next store read. The tamper methods are exactly those in Section 4.3.

**C4-05: Liveness across crash/restart.** The scenario cases in `recovery_cases.rs` are run with the process harness. Each case is run 20 times. The flakiness budget is: zero flakes allowed at 20 runs if p \< 0.01, else one flake allowed if p \< 0.05.

The liveness cases are:

| Case | Steps | Expected terminal state |
| --- | --- | --- |
| A1 | Admit, crash service mid-dispatch, restart, reconcile | `succeeded` |
| A2 | Admit, crash worker mid-compute, restart, reconcile | `succeeded` |
| A3 | Admit, complete, crash before ack, restart | `succeeded` (already committed) |
| B1 | Admit, request cancel, crash service before confirm, record exit observation, restart, reconcile | `cancelled` |
| B2 | Admit, dispatch, claim, record failure, crash, restart, reconcile | `failed` (after 3 attempts) or `succeeded` (if a later claim wins) |
| B3 | Admit, crash PostgreSQL mid-transaction, crash_restart, reconnect, reconcile | `succeeded` (if commit made it to WAL) or `retrying` (if not) |
| X1 | Admit with all checkpoints held, inject faults at every checkpoint, release randomly, verify no deadlock | all runs terminal |
| X2 | Stress: 50 concurrent admissions, random crashes, reconcile, verify every run terminal within deadline | all runs terminal |

**C4-06: Budget for the ×50 runs.** The admission and dispatch repeats (K6) must complete within a wall-clock budget recorded by the parent. The recommended budget is 5 minutes for the ×50 admission run and 5 minutes for the ×50 dispatch run, on the CI host with parallelism capped by P-PG3.

### 6.5 C5: End-to-end public durable tests

**C5-01: Durable descriptor and config.** The descriptor contains `dependencies.postgres.required: true`, `configuration.admission: durable`, and a durable readiness value. `AdmissionMode::Durable` exists and the ready receipt contains `"admission":"durable"`. A `ServiceConfig::new` with a dependency argument compiles. A config without the dependency argument does not compile in a durable doctest (compile-fail pair).

**C5-02: Readiness probe with locked admission key.** The public test sends requests while a lock helper holds the admission key. The readiness probe still returns ready. The public test then observes that only one request is admitted; subsequent requests with the same key return the same RunRef.

**C5-03: Close is not cancel.** Closing the client connection does not transition any Run to `cancelled`. A later reconnect and status check shows the Run is still `retrying` or `succeeded`, depending on timing.

**C5-04: Cancel is confirmed, not immediate.** A cancel request through the test helper returns a `CancelResult::Pending`. The Run transitions to `cancelled` only after `confirm_cancel` with a matching `termination_observation`.

**C5-05: Pinned target list.** `verify_vs001.py` checks that the exact target list from Section 8 matches the Bazel query output. No extra test targets are added without an update to the criteria.

**C5-06: Integration test list.** The MJS case driver runs all cases in `recovery_cases.rs` through the public HTTP → PostgreSQL → worker path. Each case produces the same terminal state as the store-level version.

**C5-07: Cycle-free, exact edge checks.** The `testing` crate is a Cargo member with `publish = false` and workspace lints. It has no production dependency on `foundation_echo_lib` (the normal edge is test-only). The negative check is a six-step scratch procedure: create a new Cargo workspace, add the testing crate as a path dependency, attempt `cargo build`, and verify it fails with a message about a missing `foundation_echo_lib` production dependency. The exact error text is recorded by the parent.

**C5-08: No TCP in public tests.** The public test MJS driver checks `SHOW listen_addresses` through the store observer and confirms it is `''`.

**C5-09: Reserved scans.** The `durable_boundaries.rs` reserved file contains scans for:

- no `sleep(` in C source (TestKit, Echo `src`, `tests`, testing crate);
- no `unsafe` in C source (except the known `postgres` crate block);
- the exact DSN key allowlist (C1-03);
- the exact durability settings list (C1-06);
- no `as_any` or `dyn Any` downcasts in C source (residual b);

**C5-10: Lock waiter observed.** A public test sends a request while a tamper helper holds the admission key. The test confirms that the request is queued (not rejected) and that a telemetry or log entry records the wait.

**C5-11: Worker call counts match.** The telemetry sink records exactly as many `compute_echo_artifact` calls as the store records completed attempts. The counts are compared after the scenario run.

**C5-12: Connection bound enforced.** The store uses at most `B` concurrent connections, where `B` is the bound from the durable profile (OD-6 item 4). A test that launches `B + 1` concurrent admissions observes that the `B + 1`th blocks until a connection is released. The bound is enforced by the connection pool, not by a semaphore in the store code.

## 5. Criteria by task

The criteria below are numbered by task. Each criterion has:

- a task prefix (C1, C2, C3, C4, C5);
- a sequential number;
- the expected test or evidence kind;
- the exact assertion or observation.

Failing any criterion stops the gate (S1–S12). The stop conditions are in Section 5.7.

### 5.1 C1: PostgreSQL harness, schema and durability checks

**C1-01. PgHarness owns lifecycle and cluster isolation.**

- The harness creates three distinct data directories and three distinct socket directories, each with mode 0700.
- `pg_hba.conf` contains only `local` trust lines for the declared roles, and no `host` lines.
- The postmaster listens on no TCP socket (observed by `lsof` on Darwin, `/proc/<pid>/net/tcp{,6}` on Linux).
- PIDs are registered with canonical data directories and checked for identity before stop or cleanup.
- Cleanup removes all owned data and socket directories; residue checks confirm absence.

**C1-02. Bazel-only PostgreSQL tests.**

- PostgreSQL tests are not declared as Cargo `[[test]]` targets.
- Both `services/foundation_echo/Cargo.toml` and `platform/testkit/Cargo.toml` keep `autotests = false`.
- A missing `MINDCLADE_POSTGRES_BIN` (or any of the four env keys) fails the test at runtime.
- `cargo test` does not compile or run PostgreSQL test files.

**C1-03. Exact public surface of PgHarness and PgStore.**

The exact public surface is staged per A4.5:

- **C1 harness stage:** `PgHarness::{start, start_with, dsn, stop, restart, crash_restart}`; `StartOptions` with three deadline fields; closed `Role` enum.
- **C1 schema/store/trace stage:** `PgStore::connect` and `connect_with`; `PgStore::migrate`; `PgStore::verify_durability`; DSN key rejection before I/O; `TraceContext` with its three A3.1 methods; real fixture `new`, `finish`, `observer`; public `store` field; migration checksum/version tamper helpers.
- **C2 stage:** real admission helper; admission checkpoint injection.
- **C3 stage:** real `admitted_lease`, `expire_and_reassign`, `completion`; relevant lock and tamper helpers.
- **C4 stage:** full C1-03 union, including actual `RecoveryHarness`.

No unspecified helper signature is authorized at any stage.

**C1-04. Checksum-bound schema.**

- The migration file `services/foundation_echo/migrations/0001_execution.sql` has a pinned SHA-256 checksum.
- `PgStore::migrate` acquires advisory lock `MIGRATION_LOCK_KEY`, compares the on-disk checksum, and aborts with `StoreError::IncompatibleVersion` on mismatch.
- `verify_durability` checks `fsync = on`, `synchronous_commit = on`, `full_page_writes = on`, and records `wal_sync_method`.

**C1-05. No `sleep` in TestKit or harness.**

- `PgHarness` uses `pg_ctl -w` for polling; no `sleep`, `thread::sleep`, or `std::time::Duration`-based spin loops.
- The `no_sleep` scan in `durable_boundaries.rs` passes.

**C1-06. Durability GUCs and `wal_sync_method`.**

- `verify_durability` asserts `fsync = on`, `synchronous_commit = on`, `full_page_writes = on` on every new app session.
- `wal_sync_method` is recorded and retained for both hosts.
- Under OD-4 (b), `rolsuper = false` is asserted on the app session.

**C1-07. Crash recovery performs WAL replay.**

- `crash_restart` uses `pg_ctl stop -m immediate -w`, then `pg_controldata` confirms a state other than `shut down`.
- After restart, the cluster is queryable and the recovery log shows replay.
- The harness never SIGKILLs the postmaster.

**C1-08. Provenance: all tools from one Nix store path.**

- All four canonicalized binaries lie in one `/nix/store/…/bin` directory.
- The harness rejects mismatched or missing tools.

**C1-09. Append-only events table.**

- The schema defines an events table with immutable columns.
- `UPDATE` on immutable columns is rejected; `ALTER TABLE … DISABLE TRIGGER` is not used by the store.

**C1-10. Schema version check stops on mismatch.**

- `PgStore::connect` rejects a database whose schema version does not match the expected migration checksum.
- The error is `StoreError::IncompatibleVersion`.

**C1-11. `env_clear()` on every child process.**

- Every PostgreSQL child starts with `env_clear()` plus an explicit allowlist.
- No ambient `PG*` variable, `DATABASE_URL`, or `PATH` lookup is used.

**C1-12. Socket directory length bound.**

- The created socket directory path is at most 103 bytes.
- This is verified for each cluster.

**C1-13. Immutable admission columns.**

- Schema checks reject updates to immutable admission columns, including trace fields, using legal rollback-only schema-test rows.
- Product fixture helpers do not commit fake admissions.
- C2 reruns immutability on actual admitted rows and begins `state_matches_latest_event` after every implemented operation.
- C3 and C4 extend that assertion to their real operations.
- The tamper-then-reconcile `StoreError::Integrity`/no-change negative waits for C4; no no-op reconciler is valid.

**C1-14. Direct parser and schema vectors.**

- Full direct parser/schema vectors are part of the schema/trace slice.
- No RuntimeKit trace accessor is needed for C1-14.

### 5.2 C2: Admission

**C2-01. Atomic admission with transactional outbox.**

- `PgStore::admit` inserts the Run and the outbox message in one transaction.
- A duplicate `(request_id, capability)` pair returns `AdmissionResult::Existing(RunRef)` with the same RunRef.
- A non-duplicate returns `AdmissionResult::Created(RunRef)`.

**C2-02. Idempotency key is `(request_id, capability)`.**

- The admission key combines the trusted `AdmissionContext.identity` and `WorkPacket.capability`, never request bytes.
- Retrying with the same key returns the same RunRef.

**C2-03. Admission transaction commits before response.**

- The HTTP 200 response is sent only after the admission transaction commits.
- There is no async, 202, or poll endpoint.

### 5.3 C3: Dispatch, claim, complete

**C3-01. At-least-once dispatch with inbox deduplication.**

- `dispatch_batch` selects pending outbox messages, inserts inbox rows, and marks them delivered in one transaction.
- Redelivery of the same message is rejected by inbox unique constraint.

**C3-02. Lease expiry is database-timed.**

- `Lease.expires_at` is `mindclade-utc-millis`, 24 characters.
- Expiry is checked by the database clock, not the worker clock.

**C3-03. Fenced completion.**

- `complete` locks the Run row, checks the lease matches, and commits the artifact only if the Run is still in the claimed state.
- A mismatched lease returns `StoreError::StaleLease`.

**C3-04. Completion within three attempts.**

- `WorkPacket.maximum_attempts` is at most 3.
- `record_failure` increments the attempt count and reschedules with delays of 100 ms and 500 ms.
- A Run that exceeds the attempt count transitions to `failed`.

**C3-05. Generation exhaustion at `i32::MAX`.**

- `Generation` is `i32` with minimum 1.
- Exhaustion is at `i32::MAX`; no wraparound is allowed.

**C3-06. FakeWorker and production compute equal bytes.**

- For the same `(lease, request)`, `FakeWorker::compute` and a production `work_once` commit equal bytes.
- TestKit contains no worker.

### 5.4 C4: Cancel, reconcile, recovery

**C4-01. Confirmed cancellation with observation.**

- `request_cancel` transitions the Run to `cancelling`.
- `confirm_cancel` requires a `CancelConfirmation` with a `termination_observation` SHA-256.
- The Run transitions to `cancelled` only after confirmation.

**C4-02. Reconcile processes stuck Runs.**

- `reconcile` finds Runs stuck past lease expiry, records failure or cancellation, and reschedules eligible work.
- `reconcile_once` also confirms a pending cancellation once a matching exit observation is recorded.

**C4-03. Recovery child entrypoints.**

- `recovery_child` may call only: `admit_and_wait`, `dispatch_once`, `work_once`, `reconcile_once`, `record_exit_observation`, `confirm_cancel`, `request_cancel`.
- Each has a stated production caller (Section 4.2).

**C4-04. No public cancel endpoint.**

- There is no public async, 202, poll, or cancel endpoint.
- `request_cancel` is `pub` only for the supervisor's later policy path and for tests.

### 5.5 C5: End-to-end durable execution

**C5-01. DurableAdmission implements AdmissionPort.**

- `DurableAdmission::execute` uses the real PostgreSQL path.
- It returns 200 with the exact Echo body on success.
- It returns 400/409/503 with codes `invalid_input`, `idempotency_conflict`, `unavailable`.

**C5-02. HTTP → PostgreSQL → worker path is real.**

- The generated TypeScript client drives the real HTTP endpoint.
- The service writes to PostgreSQL, dispatches to workers, and returns results.

**C5-03. Fault injection covers both fault classes.**

- Process crash: SIGKILL of service, worker, or recovery child.
- PostgreSQL crash restart: `pg_ctl stop -m immediate`, then WAL crash recovery.

**C5-04. Every Run reaches a terminal state within three attempts.**

- Once a live worker runs reconciliation, every admitted Run reaches `succeeded`, `failed`, or `cancelled`.
- A Run that stays non-terminal past the harness deadline fails the test.

**C5-05. No more than one authoritative completion per Run.**

- `complete` commits at most one artifact per Run.
- A second completion returns `CompletionResult::AlreadyCommitted(ArtifactRef)`.

**C5-06. Generated client compiles and passes.**

- The generated TypeScript client compiles against the real HTTP path.
- It passes the durable execution test suite.

**C5-07. B4 model executable check.**

- The real dependency graph matches the B4 model entries for the testing unit and external `postgres`/`nix_postgresql`.
- This is checked by the B4 boundary scan.

**C5-08. Verification script runs full suite.**

- `scripts/verify_vs001.py::run_checks` resolves `subprocess.run` at call time.
- `just verify-vs001` runs the full suite with the durable profile.

**C5-09. Compile-fail doctests flip for Durable mode.**

- After OD-6 is approved, the B3b-23 and B3b-27 compile-fail doctests flip to assert `AdmissionMode::Durable` exists and `ServiceConfig::new` takes a dependency argument.
- This is done as a parent transition like B2b-20.

**C5-10. Durable descriptor and config profile.**

- The descriptor sets `dependencies.postgres.required: true`, `configuration.admission: durable`, and a durable readiness value.
- `AdmissionMode::Durable` exists and emits `"admission":"durable"` in the ready receipt.
- The binary accepts `--postgres-socket-dir <absolute path>` in the durable local-test profile.

**C5-11. Exit code for failed dependency/migration/durability check.**

- A distinct exit code (`ExitCode::DurabilityCheckFailed`) is returned when the dependency, migration, or durability check fails.

**C5-12. Maximum PostgreSQL connections bounded.**

- The durable profile bounds the maximum number of PostgreSQL connections.
- This is checked at startup and enforced by the connection pool.
