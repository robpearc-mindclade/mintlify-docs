`runtimes.bazel` must be the unwrapped Bazel client: the package's versioned `bazel-9.1.1-<os>-<arch>` (for example `bazel-9.1.1-darwin-arm64`, a Nix PATH wrapper that execs the client binary in the same store path) or a `bazel-real`. It must never be the package's `bazel` launcher or the repository's flake wrapper. The nixpkgs launcher defaults `BAZEL_WRAPPER` to the workspace's `tools/bazel` and execs it when that file is executable, and it picks the client version from the workspace's `.bazelversion`. The flake wrapper only unsets the `BAZEL_WRAPPER` and `USE_BAZEL_VERSION` environment variables and then runs the launcher, so the launcher still falls back to `tools/bazel` and a candidate's `tools/bazel` would run on the trusted path. Admission also BLOCKS a code candidate whose `tools/bazel` or `.bazelversion` differs from base, but that is defense in depth, not a substitute for pinning the unwrapped client. The flake wrapper also passes `--server_javabase=<pinned JDK>`. P1b must confirm whether the unwrapped client needs it, and if so supply it as a reviewed fixed flag, not by routing through the launcher.

## 4. How G3's code reads this revision once adopted

1. **Selection.** The operator passes the policy PR's merge commit as `--policy-revision`. `policy-ancestry` requires it to be an ancestor of base, which is why adoption is a merge and not a branch.
2. **Validation.** Admission reads `.agents/policies/supervised.v1.json` only at that revision through its Git reader and records `policy_sha256`. `_validate_policy` accepts the bound shape. The audit's `policy` check uses the same validator; `supervised-readiness` stays BLOCKED.
3. **Pre-checks.** For a code-class packet whose earlier checks all pass, admission requires the model and source profile to be identical at base and candidate (D4; FAIL otherwise), and `.bazelrc`, `.bazelversion` and `tools/bazel` to be identical in presence, mode and bytes (BLOCKED otherwise, with no runner call). Governance packets never reach this step.
4. **Inputs.** Admission passes a copy of `boundary_evaluator` to `boundary_inputs`, which returns `(expected, tools)`. An O3-adopted implementation builds `expected` from the independent O3 anchor record and calls `load_trusted_boundary_tools(<evaluator root>, boundary_evaluator, runner=<P1b runner>, attested_facts=<O3 CI-facts reader>)`. The loader requires `sha256(<root>/boundary-evaluator.json) == config_sha256`, checks the config's exact keys and configurations against this binding, and hashes every pinned file.
5. **Cross-checks.** `tools` must be a `TrustedBoundaryTools` whose `config_sha256` equals the policy's `config_sha256`; `expected.candidate` must equal `--candidate`; `expected.model.path` must equal `model_path`; `expected.model.digest` must equal the digest of the model blob at base; `required_configurations` must equal `configurations`; `scope` must equal `required_scope`. Any mismatch is FAIL.
6. **Verification.** `verify_boundaries` regenerates the trusted host's facts, merges them with the CI-attested Linux facts, and takes Codegen's decision. On PASS, `bindings.boundary` records the report identity, including `evaluator_config_sha256` (equal to `config_sha256`) and the `hosts` provenance.

Adopting the policy alone does not enable code admission. Today `boundary_inputs`, the runner and the CI-facts reader are production defaults that raise BLOCKED, and the CLI has no flag or environment variable that can supply them. Wiring the adopted readers is a separate, reviewed O3 change. With this revision as the accepted policy and production defaults, a code packet is BLOCKED with an O3 detail (P-1).

## 7. Open items before adoption

- **P1b.** B4's `--hermetic` collection must collect the candidate at `cwd`, load its helpers from the evaluator root, resolve tools from the pinned runtimes and use the provisioned caches. B4 today rejects `--hermetic`. P1b also has to confirm how the collector learns the provisioned repository cache (no B4 flag carries it), and whether Cargo needs a writable `CARGO_HOME` for its package-cache lock while the sandbox allows writes only to the step directory. The pinned `runtimes.bazel` must be the unwrapped client (§2), and the rest of the P1b contract is in [governance tools](/developer/governance-tools#p1b-and-b4-dependencies).
- **Helper pins.** `frontend_action.py` and `typescript_loader.cjs` need a reviewed binding, either a config-schema pin or another mechanism.
- **O3 anchors and readers.** The independent anchor record, the production `boundary_inputs`, and custody for the CI facts archive.
- **Artifact envelope.** The CI facts archive is decoded under G1's ZIP rules (no data descriptors, extra fields or ZIP64). O3 should confirm that a real `boundary-facts-<run_id>-<run_attempt>` download meets them.
