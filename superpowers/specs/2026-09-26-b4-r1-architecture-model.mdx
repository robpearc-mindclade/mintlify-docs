## 2. Method and its limits

The parent drafted this model with a scratch evaluator that approximates §6 stages 4–5 over both hosts' facts. It covers:

- owner resolution: membership, then path, then unit;
- transparent filegroup and alias hops, keeping the first hop's kind;
- allow and deny, including roles;
- production-to-test and public-to-internal;
- the external allowlist, using the §7.3 key derivation;
- computed and unresolved imports;
- component cycles;
- coverage.

The evaluator is kept out of the repository ("no second architecture parser", §1). It lives beside the evidence as `r1-drafting-aid/`. Codegen alone decides. The binding check is B4-19's real-graph pass in Stage 2.

Against the approved-at-freeze §8 text, the evaluator reports the following on both hosts:

- 4 ownerless endpoints;
- 2 coverage diagnostics;
- 8 production-to-test edges;
- 35 unapproved dependencies (12 distinct);
- 68 unapproved externals (26 distinct);
- 1 production computed import.

Against the model below, it reports zero violations on both hosts, with three expected exceptions. The first is the one computed import in R1-08, which needs your decision. The second is six production-to-test edges that the build change F-1 removes. The third is one `facts-coverage` line for `//codegen:boundaries_tests`, which clears when Stage 2 removes its `manual` tag (R1-05).

## 3. Reconciliation items (§8 → R1)

Each item cites one observed example; the counts are the same on both hosts.

- **R1-01 `//:REPO.bazel` joins `tools.build`.** Three conformance targets and `codegen:library` reach it through `//:generator_inputs`, and today it would be an ownerless endpoint. Example: `codegen/BUILD.bazel:13` compile_data.
- **R1-02 Foundation Echo memberships use the real labels.** The §8 label `//services/foundation_echo:service` does not exist, and would be a `facts-coverage` failure. The real labels are `//services/foundation_echo:foundation_echo_lib` (the library, crate `mindclade_foundation_echo`) and `//services/foundation_echo:foundation_echo` (the binary). The Cargo membership `mindclade-foundation-echo` is unchanged.
- **R1-03 New unit `services.foundation_echo#tests`** (`services/foundation_echo/tests`, scope test). Without it, `tests/process.test.mjs:29`'s computed `import()` is a production-scope `computed-import`. With it, the import is listed in `test_dynamic_imports`, as §6 intends for tests. It also carries the process test's Node builtins.
- **R1-04 `tools.validation` becomes role `build`, scope `production`.** §8 had role `conformance`, scope `test`. `codegen:library` has a **build** edge to the collectors: its compile_data reaches `//:generator_inputs`, which contains `tools/validation/{dependency_facts.py,typescript_facts.mjs}`, per the B4-21 inventory rule. A test-scope target makes that edge a `production-to-test` violation. The collectors are build tooling that Codegen digests, so they are production scope. Their fixtures stay excluded.
- **R1-05 No exclusion for `//codegen:boundaries_tests`.** The probe lists it as unanalyzed, because it is `manual` while its reserved tests are RED. Excluding it would hide the edges of a target that must run in CI (B4-15). Instead, Stage 2 removes its `manual` tag, as a parent BUILD change, before the binding real-graph check. Until then the drafting check shows one expected `facts-coverage` line for it.
- **R1-06 Allow edges §8 did not list.** Every one is observed, and none overlaps a mandatory deny (checked mechanically against B4-19's invariant):
  - `codegen.compiler → tools.validation` (build). This is the R1-04 inventory edge.
  - `codegen.compiler → architecture.docs` (test). `codegen:service_http` reads the real `architecture.yaml`.
  - `codegen.compiler → services.foundation_echo` (test). `codegen:service_http` has `//services/foundation_echo:sources` as data (`codegen/BUILD.bazel:177`), which covers `src/{composition,lib,main,ports}.rs`, for the declared-source scan. This is test-only, and the only such edge.
  - `tests.conformance.vs001 → platform.runtimekit` (production and test). The B3b composition driver, config forgery and compile-fail probes link RuntimeKit. The suite is test scope.
  - `tests.conformance.vs001 → tools.validation` (test). `composition_driver` data.
  - Test kinds alongside approved production edges:
    - `platform.runtimekit → core` (`config_tests`);
    - `platform.testkit → core` and `platform.testkit → runtimekit`. TestKit is `testonly`, so every edge from it is test kind;
    - `services.foundation_echo → core` and `services.foundation_echo → generated.projections` (the compile-fail and config-mutation tests).
  - `services.foundation_echo → tests.conformance.vs001` (test). The `config_mutations` genrule runs `tests/conformance/vs001:service_config/mutate.py`. It is test-only, so it cannot form a cycle.
- **R1-07 Externals are exactly the observed set** (40 entries), listed in §6. Changes from §8:
  - **Crates:**
    - `httparse` for `platform.runtimekit` (production). This is the B3b transport crate you approved.
    - `serde` and `serde_json` for `services.foundation_echo`.
    - Test kinds for codegen, runtimekit and conformance crates. Bazel `rust_test` deps are test kind.
  - **Bazel:**
    - `rules_rust` needs **production** as well. `rust_library` and `rust_binary` have public `allocator_libraries` and `malloc` attributes pointing into `@rules_rust`, and the §6 kind table classes non-underscore attributes as production.
    - `rules_cc` (the `local_config_cc` host toolchain) is needed on both hosts.
    - `nix_protoc` and `nix_protobuf_python` for conformance (test). These are the B2b `[R]` repos.
    - `platforms`, `rules_nixpkgs_core`, `nix_cc` and `bazel_skylib` were never observed as direct externals, so they are omitted.
  - **npm:** `@typespec/compiler` and `@typespec/http` are observed as production only. The `build` kind from §8 is dropped, because no type-only import was observed.
  - **Node builtins:** each is listed with its exact observed `from` set. The public unit gets none.
- **R1-08 (your decision) The TypeScript collector's computed `require`.** The §6 YAML below already carries option (a)'s exclusion as exact bytes. Option (b) replaces that entry with `tools/validation/typescript_facts.mjs`, and option (c) removes it. `tools/validation/typescript_facts.mjs:219` loads the pinned TypeScript compiler through `createRequire(import.meta.url)(values.get("--typescript"))`, a provisioned Nix-store path given on the command line. Under R1-04 that file is production scope, so this is a `computed-import` violation. No model entry can permit it, because §6 has no computed-import allowlist. The options:
  - **(a) Recommended.** The Stage 2 implementer moves only the pinned-compiler loading into a new file, `tools/validation/typescript_loader.cjs`, and `typescript_facts.mjs` imports it by a literal path. The model excludes only the loader; the rest of the collector stays observed. Conditions:
    - The loader is outside the implementer's §2 file list, so the parent delegates it explicitly.
    - It joins `//:generator_inputs`, `scripts/validate_generator_inputs.py` and the facts `collectors` digests, so G3's collector identity covers it.
    - A unit test pins the loader to a single `require` with no other import.
    - It exists before the first facts check. An exclusion absent from the inventory is a model error.

    Cost: one small collector change plus one narrow exclusion, both re-reviewed.
  - **(b)** Exclude `tools/validation/typescript_facts.mjs` itself. No code change, but the collector's own imports go unobserved, and so does Codegen's build edge to that file. It is also the only non-fixture TS file under the `tools/validation` membership, so excluding it risks an unobserved-membership `facts-coverage` failure.
  - **(c)** Amend the criteria to add a narrow computed-import allowlist. This is a criteria change and needs re-review.
- **R1-09 Maturity of the B3b components moves from `planned` to `partial`.** This covers `platform.runtimekit`, `platform.testkit` and `services.foundation_echo`, and matches `maturity.yaml` after B3b. It is non-durable, partial VS-001. The label grants no proof (source profile). New components are `partial`.
- **R1-10 The forbidden list gains `tch`,** beside `tch-rs` and `Triton` (§5).

**Build change F-1 (parent-owned BUILD edit in Stage 2; your decision alongside R1).** `codegen/frontend/typespec:sources` globs `test/*.mjs`. The production `typespec_compile` targets `:echo`, `:vs001` and `:vs001_services` therefore take the frontend tests as inputs. That gives 6 `production-to-test` edges into the `codegen.compiler#frontend-tests` unit. The fix:

- split `test/*.mjs` into a `test_sources` filegroup;
- `typespec_test` takes both filegroups.

`composition_driver`, `protocol_driver` and `service_driver` also consume `:sources` (`tests/conformance/vs001/BUILD.bazel:49/83/217`). They get `:test_sources` too if they need the test files. The re-probe after F-1 must show zero production-to-test edges. The fallback is to drop the `frontend-tests` unit, but then production code could import test helpers without detection. F-1 changes action inputs only. Generated bytes should be unchanged, and the Stage 2 regeneration is required anyway (B4-21).

**§13 A (confirm).** The virtual root `Cargo.toml` is not a Cargo member. The parent reads §6 stage 4's "member manifest or excluded" as satisfied by `tools.build`'s file-label membership `//:Cargo.toml`, which declares ownership only (§5 membership placement). The reserved test `uncovered_sources_and_ecosystems_fail` already pins this reading.

**Parser point for Stage 2 (no policy effect).** R1-07 repeats an `(ecosystem, name)` pair when the `from` sets have different kinds: `serde`, `serde_json`, `bazel_tools`, `nix_frontend_deps`, `nix_rust`, `rules_cc` and `rules_rust`. §5 does not forbid this, and the only normalised-duplicate rule is for `forbidden` names. The Stage 2 parser must accept disjoint repeats. If the reviewer rules otherwise, merge each pair to the union of kinds. That is a small loosening; for example, `core.semantic-kernel` would gain `serde` in test kind.

## 3a. Independent review response (2026-09-26)

**Verdict:** APPROVE WITH CHANGES. The reviewer used its own §6 evaluator, independent of the drafting aid:

- It re-derived the kind of all 2770 and 2771 edges with zero mismatches.
- On both hosts it reached the same result as this proposal.
- Coverage was clean, the externals equal the observed set, and the mandatory-deny invariant holds.
- It found no forbidden transitive names.

Changes applied:

- **Important 1:** option (a)'s loader exclusion is now in the §6 YAML as exact bytes, and its conditions are listed in R1-08.
- **Important 2:** the fixture file `tools/validation/fixtures/boundaries/ts/app/kernels.ts:1` puts an `unresolved:triton` node in both hosts' facts. Exclusions remove edges, not nodes. Parent ruling L in B4 criteria §13 settles this: `forbidden-external` matches only the endpoint types in the §6 parenthetical (workspace, crate, npm, Bazel repo), never `unresolved:` or `computed:`. Those are covered by `unresolved-import` and `computed-import`.
- **Minor 1:** allow kinds that were never observed are removed:
  - `codegen.compiler → contracts.registries [production]`;
  - `platform.runtimekit → tools.build [build]`;
  - `platform.testkit → tools.build [build]`.

  `platform.runtimekit → platform.testkit [test]` stays as explicit ADR-008 intent: TestKit is allowed only as a RuntimeKit test dependency.
- **Minor 2:** no `//codegen:boundaries_tests` exclusion (R1-05).
- **Minor 3:** the R1-06 text is corrected.
- **Minor 6:** parent ruling N in §13 pins the §7.3 key derivation for bare `@@bazel_tools` and for `rules_rust++…` extension repos.
- **Minor 7:** F-1 is extended to the conformance drivers.
- **Repeated `(ecosystem, name)` pairs:** parent ruling M in §13 accepts them, provided their `from` sets are pairwise disjoint.
- **Minors 4, 5 and 8:** no change. Both test-only couplings keep their testonly protection. B3b moved past `bd692b2` only in docs, scripts and generated manifests, and the re-probe on merged `main` stays binding.

**Declined by the reviewer, and left for Rob or later:**

- whether the ADRs endorse the two test couplings;
- whether generated bytes stay unchanged under F-1 (the Stage 2 regeneration answers this);
- external `from` lists are per component, not per unit. This is a criteria limitation: a Node builtin seen only in a test unit is allowed for the whole component.
