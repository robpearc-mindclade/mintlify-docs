## 3. Interfaces (proposed unless marked existing)

### 3.1 Topology (Q1, an owner decision)

The profile is **additive**. The test descriptor, its products and the binary's behaviour stay as they are. A second authored descriptor yields a second constructor and a second inspection. `:foundation_echo` stays one binary: `[]` runs the test profile, and exactly `["--postgres-socket-dir", P]` runs the durable profile.

**Codegen rule: one descriptor per (identity, profile).** The source path alone selects the profile: `service.descriptor.yaml` is the test profile, and its validator stays byte-unchanged; `service.durable.descriptor.yaml` is the durable profile.

Today four sites allow exactly one descriptor: `seal_services` (`codegen/src/graph.rs:270-272`, which reports `descriptor-binding` for a second identity); `emit/service_http.rs:55-60`; `emit/mod.rs:61-67`; `projection.rs:402-416`.

C0 changes them as follows:

- **`seal_services`** keys on (identity, profile), so a same-profile duplicate is still `descriptor-binding`. It also reports `descriptor-pair`, at the durable value, when any field outside the four §3.2 deltas differs from the test descriptor.
- **The adapter** is emitted once, from the test descriptor. Its operation and `max_body_bytes` are shared with the durable descriptor.
- **Inventory.** `vs001_services` carries both files, so every profile compiles both. Only `DurableComposition` publishes durable products, and it reports `descriptor-inventory` if the durable file is missing.

### 3.2 The durable descriptor (`FoundationEchoDurableAdmission@v1`)

These are the only deltas from the test descriptor. Key sets stay closed. A test-only value is `descriptor-profile`, a value out of range is `descriptor-range`, and a missing or extra key is `descriptor-field`.

```yaml
dependencies:
  postgres: {kind: postgresql, required: true, max_connections: 13}
configuration:
  admission: durable
  lifecycle: {request_timeout_ms: 2000, shutdown_timeout_ms: 5000}
  execution: {worker_claims: 4, dispatch_batch: 16, lease_ms: 30000, request_deadline_ms: 10000}
health: {readiness: durable-admission}
```

### 3.3 Products

- **Variant.** `DurableComposition` (`VS001DurableCompositionProducts@v1`) is a new closed variant after `Composition`, selected by `generate_vs001.py --composition --durable`. A downgrade is rejected under the existing lock and in recovery, with `projection-profile`.
- **Catalog.** 16 files: the 14 existing ones plus `service/durable/{config.rs,descriptor.json}`. There are 15 output hashes and 2 `descriptor_inputs`.
- **`service/durable/descriptor.json`** keeps the shape of service-config-v1 §3: `profile` is `FoundationEchoDurableAdmission@v1`, and `source` is the durable path; `config.admission` is `"durable"`, and `config` keeps exactly its nine fields; the five integers go in a new closed top-level object, `durable`: `worker_claims`, `dispatch_batch`, `lease_ms`, `request_deadline_ms` and `max_connections`.

### 3.4 Bounds, sessions and B (Q2 and Q3, owner decisions)

| Bound | Key | Recommended | Accepted range (Codegen and `DurableConfig::new`) |
| --- | --- | --- | --- |
| HTTP in flight | `resources.max_in_flight` | 8 (shared field) | 1..=64 (existing) |
| Worker claims | `execution.worker_claims` | 4 | 1..=16 |
| Dispatch batch | `execution.dispatch_batch` | 16 | 1..=256 |
| Lease | `execution.lease_ms` | 30000 | 1000..=300000 |
| Request deadline | `execution.request_deadline_ms` | 10000 | `request_timeout_ms`..=30000 |
| Connections B | `postgres.max_connections` | **13** | `= max_in_flight + worker_claims + 1`, ≤ 24 |

**Session partition** (a C-owned interface, proposed here). The app-role sessions open at startup in three fixed partitions. Nothing borrows across partitions, and each checkout waits, under a deadline, only on its own partition.

- **Admission: `max_in_flight` sessions.** A request holds one only for its admission transaction and releases it at commit or rollback. It then waits for the terminal state on an in-process signal, holding **no** session, and checks one out again to read the artifact.
- **Worker: `worker_claims` sessions.** Each is held from claim until the completion or failure commits.
- **Control: one session.** The scheduler loop holds it for dispatch, reconciliation and exit observations.

**Why B = 13.**

- **13 is the maximum concurrent use**, so no class ever waits on another.
- **B = 12 with release at commit only delays:** dispatch can wait on an admission's commit.
- **Holding sessions across the wait deadlocks:** at 12 in C5-12, eight waiting admissions and four workers starve dispatch.
- **Headroom.** The cap of 24 leaves room, within C §4.2's `max_connections = 32`, for four test sessions and three reserved slots.
- **The admin migration session** closes before readiness and is not counted.

OD-6 approved B = 12, so changing it is a stop for Rob (Q2).

### 3.5 RuntimeKit

**Configuration.**

- **`AdmissionMode { Test, Durable }`.** `ServiceConfig::new` keeps its eleven arguments and its **eight** checks (`tests/config.rs:476`), its nine `ConfigError` variants with their texts, and its purity.
- **`DurableConfig`** owns a Durable `ServiceConfig`. It has private fields and no `Default`, `Deserialize` or builder. Its constructor is `DurableConfig::new(listen, service, tenant,
  environment, descriptor_digest, max_body_bytes, max_in_flight, request_timeout, shutdown_timeout,
  log_level, worker_claims, dispatch_batch, lease, request_deadline, max_connections) ->
  Result<DurableConfig, DurableConfigError>`. It has **no mode parameter**. It calls `ServiceConfig::new(…, Durable, …)`, so a Test config can never pair with durable limits. It checks, in order: the eight `ServiceConfig` checks, then the five §3.4 ranges (in integral milliseconds), then the B equality and cap. Accessors: `service() -> &ServiceConfig`, and one per limit.
- **`DurableConfigError`.** Variants: `{Config(ConfigError), Admission, WorkerClaims, DispatchBatch,
  Lease, RequestDeadline, MaxConnections, Arguments, PostgresSocketDir}`. Codes: `Config(e)` delegates `code()`. The others are `config-admission`, `-worker-claims`, `-dispatch-batch`, `-lease`, `-request-deadline`, `-max-connections`, `-arguments` and `-postgres-socket-dir`. `Display` texts are fixed and never echo input, and `source()` is `None`. `Config(e)` has its own nine texts with "invalid durable-profile" naming, never the "TestAdmission" ones.

**Telemetry.**

- **`Event.code`** (`telemetry.rs:191`, set at `:222-225`) widens from `Option<ConfigError>` to a private `Option<Code>`, where `Code` is `Config(ConfigError)` or `Durable(DurableConfigError)`. `code()` keeps its signature.
- **New constructors:** `Event::durable_config_error(ts, e)` emits `config_error`; `Event::dependency_error(ts, DependencyFailure)` emits `dependency_error`, with reason `unavailable`, `migration`, `durability` or `integrity`; `Event::attempt(ts, AttemptEvent)` emits `attempt_started` or `attempt_committed` (C5-11).
- **`serve`** applies its identity rule to `Durable` as well.

**HTTP.** `Request::trace_fields() -> TraceFields<'_>` returns every raw `traceparent` and `tracestate` value, in the order received and with surrounding whitespace trimmed.

- The existing head bounds still apply: 8192 bytes and 32 fields.
- The values never reach telemetry.
- Only C's `TraceContext::from_fields` parses them (A3.1).

### 3.6 Echo

- **Generated constructor.** `generated/vs001/service/durable/config.rs` defines `pub fn
  build_durable_service_config() -> Result<DurableConfig, DurableConfigError>`, following service-config-v1 §2 with the §3.2 literals. It uses no panic, `unwrap` or dynamic lookup.
- **Argv.** `main.rs` accepts exactly `[]` or `["--postgres-socket-dir", P]`. Anything else is `Arguments`, which exits 3 (Q8).
- **Supervisors.** `supervise_durable(build: fn() -> Result<DurableConfig, DurableConfigError>,
  socket_dir: &OsStr) -> Stopped` is proposed. A test builder cannot be passed to it; `supervise_with` (`lib.rs:256-282`, which builds `TestAdmission` at `:282`) gains a guard: if `admission()` is not `Test`, it exits 3 with `config-admission` before building any port.
- **Socket directory P.** It is checked with std only: no `unsafe`, no crate, no environment variable. A failure is `PostgresSocketDir`, and no connection is attempted. P must: be absolute UTF-8 with no whitespace, quote, backslash or control character; be a real directory under `symlink_metadata`, with mode `0o700`; be owned by the effective uid, established std-only (for example, from a probe file that is created and removed inside P); give `P/.s.PGSQL.5432` of at most 103 bytes.
- **Constants.** Roles: `mindclade_admin` and `mindclade_app`. Database: `mindclade`. Port: 5432. `application_name`: `mindclade-foundation-echo:{migrate,admission,worker,control}`. DSN keys: `host`, `user`, `dbname` and `application_name` (C1-03).
- **Durable startup,** with the exit code for a failure at each step: argv (3); the constructor (3). P (3); an admin session runs `verify_durability` and `migrate`, then closes (6); the §3.4 app sessions open and pass `verify_durability` (6); `compose` with `DurableAdmission`, then bind and identity (4); the engine starts; the ready receipt.
- **Exit codes.** 0, 1, 3, 4 and 5 are unchanged. `EXIT_DEPENDENCY = 6` applies to the durable profile only, and only before readiness. Its reasons: `unavailable`: refused, no socket, or a missing role or database; `migration`: checksum, version or apply; `durability`: `verify_durability`, or `rolsuper` on the app role. After readiness, a dependency loss gives 503 and a `dependency_error`, never exit 6. Exits 3, 4 and 6 write no receipt.
- **Receipts.** The ready receipt keeps its four `FoundationEchoReady@v1` keys, with `"admission":"durable"` and the durable descriptor's SHA-256. Stdin control and `FoundationEchoStopped@v1` are unchanged.
- **P1 digest source.** `DurableAdmission` sets `Admission.capability` to `{identity:
  AdmissionContext::identity(), digest: AdmissionContext::descriptor_digest(), target_kind:
  "capability"}`. It takes `tenant` and `environment` from the context, never from request bytes.
- **Trace plumbing.** The generated adapter stays unchanged. T1 proposes a hand-owned `http.rs` trace-accessor addition with different signatures (`traceparent_fields()` and `tracestate_fields()`, each returning `Vec<&[u8]>`), whereas C0 requires `Request::trace_fields() -> TraceFields<'_>`. C0 must reconcile that interface after T1's separate review and owner decision. Per request, the composition binds `request.trace_fields()` into its `BoundAdmission` before it calls `echo_handler`. `AdmissionPort` gains a provided method, `execute_traced(&self, context, request_id, request, trace)`. Its default calls `execute`, so `TestAdmission` and B3b's ports compile unchanged; `DurableAdmission` overrides it and passes `TraceContext::from_fields(…)` to `Engine::admit_and_wait`, beside the `AdmissionContext` and never inside it.
- **The C5 harness** reads P only from the `host=` value of `PgHarness::dsn(Role::App)`, so `PgHarness` gets no new item. It sets decoys for `PGHOST`, `PGPORT`, `PGUSER`, `PGDATABASE`, `PGOPTIONS` and `DATABASE_URL`.
