## Authority and boundaries

Linear owns engineering work scope, assignment, blockers and closure. Git owns reviewed technical authority. The repository-owned [Linear task template](/developer/linear-task-template) captures the human work contract, while the [architecture documentation workflow](https://github.com/Mindclade-org/mindclade-internal-monorepo/blob/main/.agents/workflows/architecture-docs.md) defines how active documentation is authored and reviewedLinear owns engineering work scope, assignment, blockers and closure. The repository-owned [Linear task template](/developer/linear-task-template) captures the human work contract, while the [architecture documentation workflow](https://github.com/Mindclade-org/mindclade-internal-monorepo/blob/main/.agents/workflows/architecture-docs.md) defines how active documentation is authored and reviewed.

Automation does not grant execution, admission, release or publication authority. It does not call the Linear API from CI, create a second task register, amend accepted ADRs through prose, or treat a generated projection as an authored sourceAutomation does not grant execution, admission, release or publication authority. Generated files remain derived from their authored inputs and generator. Historical records remain bound to their original date and scope. Scaffold presence remains planned until its existing activation gate is reviewed and satisfied.

## What the static check owns

The repository check `scripts/validate_documentation_automation.py` verifies a small set of integration invariants that are not semantic architecture compilation:

- the task template still exposes the required H2 contract headings;
- the architecture workflow keeps its required H2/H3 headings outside fenced examples;
- the architecture prompt keeps its required field labels inside the shared fenced `text` contract block;
- the architecture evaluation keeps its required first-column table labels;
- this guide links to each governing source;
- `just check` and `just verify` both invoke `verify-doc-automation` first.

## CI integration

The existing [Executable Foundation workflow](https://github.com/Mindclade-org/mindclade-internal-monorepo/blob/main/.github/workflows/foundation.yaml) runs `just verify` for pull-request, merge-group and main evidence. Documentation automation is therefore part of the existing verification graph instead of a second required GitHub Actions workflow. ## Extending the contract

Add an invariant only when it protects an existing repository authority boundary. For a new invariant:

1. write or change its regression test first and observe the expected failure;
2. make the smallest validator change that satisfies that test;
3. update this guide when the operator or contributor workflow changes;
4. refresh the mechanical repository tree when tracked paths changed;
5. run the narrow checks and the task's required parent-owned verification;
6. obtain fresh whole-candidate review before governed publication.

Do not add live Linear reads, implicit network dependencies or generated-document rewrites to this static check. Cross-system synchronization belongs to the connected integration layer and remains subject to its own credentials, evidence and failure handling.

## Failure behaviour

A missing governing file, structurally missing anchor, missing guide link, or misordered/missing Just recipe dependency returns exit status 1 with the violated contract detail. Text mode writes the first failure to stderr. `--json` mode writes one parseable report to stdout, emits no diagnostic prose to stderr, and still exits 1 when any named check fails.
