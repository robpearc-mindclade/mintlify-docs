This template defines the content of one Linear engineering task, completed before admission. Whoever prepares a task for admission, and its reviewers, use this template.

<Info>
  This is a human template; it is not WorkPacket@v1 serialization, an execution grant or a second task register. Use this content in one Linear task. Git owns the reviewed technical contract; Notion links provide context.
</Info>

Complete the fields before admission using the [supervised development procedure](/developer/supervised-development). Unresolved fields are blockers, not implied approval. Its dependencies, evidence and tool/network/environment prompts belong in specification, acceptance descriptions, stop conditions or operator records, not extra fields in the frozen packet schema.

The governance implementation uses [MIN-14](https://linear.app/mindclade/issue/MIN-14/vnext-establish-supervised-engineering-authority-and-enterprise), last recorded as In Progress. Refresh its live assignment and state before dispatch. Keep its acceptance blockers visible; this template does not request or record closure.

## Acceptance before implementation

For each criterion record the observable result, independent expected result, reviewer/evaluator identity and revision, evidence required, and failure cases. Distinguish source, remote CI, protected review, runtime, scientific, release and deployment scopes. Name the required checks and use the documented commands in the [WorkPacket contract](/developer/work-packet-v1) and [governance tools](/developer/governance-tools), subject to review and operator adoption. Under parent-owned execution, the parent runs validation and supplies receipts to reviewers.

Keep the task open or blocked while any required step is unavailable. The 2026-09-23 SAML/protection blockers prevent end-to-end closure and evidence publication. A source-complete report may be recorded as progress without claiming supervised readiness or independent scientific/release assurance.

## Linear ↔ GitHub integration verification

When the integration itself must be verified, use a bounded documentation-only change tied to a dedicated Linear issue rather than an unrelated production change. Create the branch from Linear's generated branch name so the issue identifier is present, publish the protected PR through the repository's authorized GitHub App, and preserve the normal CODEOWNER, required-check and merge-queue gates.

Treat status transitions as evidence, not authority: draft/open may move the Linear issue to In Progress, ready-for-review may move it to In Review, and only a successful protected merge to `main` with the issue closing reference may close the task as Done. Confirm the PR remains linked in both Linear and GitHub after the merge; automation never waives repository governance.
