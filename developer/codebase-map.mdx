This page shows which components are implemented, where they live, and how they connect, from authored contracts to the conformance suite. It describes `main` at commit `72b762d`; the crate manifests it cites are unchanged at `main` `1fe3c1a` (the closeout merge), where B4 dependency enforcement (PR #22) has also merged. The platform is an experimental, partial foundation. B3b is **non-durable partial VS-001**. Nothing here is production, release, deployment, or scientific readiness.

This page is a map, not an authority. Design lives in the [system design](/architecture/system-design), maturity in [maturity.yaml](https://github.com/Mindclade-org/mindclade-internal-monorepo/blob/main/docs/architecture/maturity.yaml), and task status in the [current task register](/developer/agent-handoff#current-task-register). Each component's README has its detail.

Reading the diagram: down to the generated products, arrows show data flow. In the bottom boxes, `composes` means Foundation Echo depends on RuntimeKit, `&lt;-` means TestKit depends on RuntimeKit, and `^ tests only` means only Echo's tests use TestKit. Every box is an existing path at `72b762d`, except `TS caller`, which stands for any external caller of the generated client.

### Text equivalent

1. **Authored inputs.** The public contract `contracts/typespec/public/echo.tsp`, the internal TypeSpec under `contracts/typespec/internal/`, and the foundation baseline `contracts/fixtures/foundation/echo.tsp` are the semantic sources. The Echo descriptor `services/foundation_echo/service.descriptor.yaml`, the architecture model `docs/architecture/model/architecture.yaml`, and the two Proto field registries in `contracts/registries/` are the other authored inputs.
2. **TypeSpec frontend** (`codegen/frontend/typespec`). It runs the official TypeSpec compiler once and writes `SemanticInput@v1` JSON. The Bazel targets are `:echo` (foundation), `:vs001` and `:vs001_services` (which also stages the descriptor bytes).
3. **Codegen** (`codegen/`, which uses the kernel in `core/`). It reads the frontend output plus the architecture YAML and registries. It validates them, seals one immutable `MindcladeGraph@v1`, lowers borrowed views into a target IR, runs the emitters, and publishes through its owned publisher. It is the only semantic compiler.
4. **Generated products.** `generated/foundation/` (2 files) and `generated/vs001/` (14 files) are written only by Codegen.
5. **Consumers.** Callers use `public/client.ts`. The Foundation Echo crate compiles `rust/mod.rs`, `service/http.rs`, and `service/config.rs` into itself. The conformance suite reads all products independently.
6. **Runtime.** Foundation Echo composes the generated HTTP adapter over RuntimeKit, with the in-memory `TestAdmission` port. TestKit is test-only and used only by tests. RuntimeKit depends on neither TestKit nor Echo.
7. **Build layer.** Nix pins the tools. Bazel imports them as `@nix_*` repositories and runs the builds and tests. Cargo runs the workspace tests. The `justfile` recipes call the `scripts/` drivers.

## Dependency direction today

From the crate manifests and Bazel rules at `72b762d`:

- `core` depends on no workspace crate.
- `codegen` depends on `core`. It is the only semantic compiler. RuntimeKit and the service consume compiled Rust configuration and never parse TypeSpec or YAML at runtime.
- `runtimekit` depends only on `core` and `httparse`. `//platform/runtimekit:dependency_tests` checks that it stays free of Echo, Codegen, YAML, and TestKit.
- `testkit` depends on `core` and `runtimekit`, and is `testonly`.
- `foundation_echo` depends on `core`, `runtimekit`, `serde` and `serde_json`. It takes TestKit only as a dev-dependency. `:composition_in_process` checks, through the `binary_deps` genquery, that the binary's closure excludes TestKit.
- The conformance crate depends on `core` and compiles the generated Rust sources.
- The generated TypeScript client has no package dependencies.

These are local checks on specific crates. Repository-wide enforcement is B4, merged through PR #22: `just verify-boundaries` collects the running host's actual Cargo, Bazel, and TypeScript dependencies and has `codegen check-boundaries` check them against the `allow`, `deny`, and `external` rules of `docs/architecture/model/architecture.yaml`, in every `just verify`. The two-host matrix passed once for B4's head `a08e802` (receipt on PR #22); each candidate that governance admission consumes needs its own.
